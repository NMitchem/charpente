# Changelog

## 0.5.0 (unreleased)

### Breaking changes
- **`App::begin_group` takes the step's `WallTime`.** `App::begin_group(now)` (and the crate-private job group) hands every transaction staged into the group its `tx.now()`; a caller passes the time it already holds, `handle_at`'s `now` or a kernel arm's `now.wall`. A test that calls `begin_group()` on an App adds one, `WallTime::UNIX_EPOCH` if it has none in hand.

### Changed
- **`charpente test --mutants` outside charpente's own workspace refuses a run that gives no `--test-package` or no `--file`, and names the command that works.** The verb's defaults are charpente's own. Without `--test-package` it judged every mutant with `charpente-core` and `charpente-sim`'s tests, whose published suites do not build outside this repository, so an agent running a plain `charpente test --mutants` in its app crate on 0.4.0 got 21 compile errors, and nothing said `--test-package` was the fix. Without `--file` it mutated `crates/charpente-core/src/log.rs` and `crates/charpente-sim/src/checks.rs`, which are not in an app's tree. When the workspace has no member named `charpente-core`, the verb now exits 2 before the install check, naming the missing flags, why each default does not exist there, your package (the one at `--dir`, else the workspace's only one) and the command to run, which keeps every flag given and adds the missing ones. Inside charpente's repository nothing changes, and when `cargo metadata` fails the run goes on to cargo's own error as before. GUIDE §8 says so.
- **GUIDE §8 says a request `Drive` re-sends takes effect at the tail's start, not at its offset, so a check that judges timing treats it as landing after the faulted phase.**

### Added
- **`tx.now()`: a transaction reads its step's held wall time.** Every route, job and job a schedule enqueued in one kernel step reads the one `WallTime` the loop held at the step's start, through `Tx::now` (and a tenant-scoped transaction's deref), with no change to any log record. On a follower's read route it is the follower's own held reading. `Db::transact` and `Db::begin_group` carry no time and `tx.now()` there panics by name; `Db::transact_at(now, f)`, `Group::set_now(now)` and the hidden `App::transact_for_tests_at(now, f)` give one. A node whose clock is behind by less than the time since the store's newest recorded time plus `CLOCK_TOLERANCE` opens unnoticed, about 24 h plus 60 s for an app with no keys and no schedule of its own, so a timed obligation can run late by that much. DESIGN §1 and §2 and GUIDE §7 state it.

- **`tx.enqueue_at(at, job)` and `tx.enqueue_after(delay, job)` carry a job's due time in the log (record tag `0x0e`).** `enqueue_after` is `tx.now()` plus the delay, saturating at the far future, and refuses by name where `tx.now()` does. A past time is due at once. `ScopedTx` has both; there is no keyed or cross-tenant timed variant yet. The time reaches `JobRow.due_at` and `Enqueued.due_at` (`Db::drain_enqueued`), and `Store::materialize_job` gains a `due_at` argument. An enqueue without a due time is recorded byte for byte as in 0.4.0. `PROTO_VERSION` is 8 and `MANIFEST_FORMAT` is 5, so a 0.4 peer or archive is refused by name. The dispatcher honouring the time is the next change; GUIDE §6 "Due at a time".

### Fixed
- **`charpente new`'s usage line says the scaffold has three sim properties.** It said two from 0.3.0, when the event check made three; a unit test now counts the template's checks.

## 0.4.0 (2026-11-01)

### Breaking changes
- **`Kernel::into_app` is gone, so a second kernel on a spent `App` does not compile.** Building a kernel moves the App's job definitions, outbound hosts and cron entries into it. A `Kernel::new` on the App `into_app` handed back answered requests and nothing else: it ticked no cron, and a job enqueued on it stayed Pending with `job "…" is not registered — add it to the jobs![…] list passed to App::mount_jobs`, which sent the reader to a list that already named the job. A kernel now keeps its App for life. Read the end state through `kernel.app()` (`kernel.app().db().snapshot()`), which is no longer hidden from the docs, or `kernel.app_mut_for_tests()`; a helper that returned the `App` returns the `Kernel`. To go on after `run`, run the same kernel again against another `SimSource`, or restart (`sim.restart_process()`, or `sim.restart()` for a power cycle), rebuild the app and build a new kernel. GUIDE §8 says when each fits.
- **The human failure block drops its `config:` line and labels the unshrunk message `before shrinking:`.** The line was a dump of every fault rate, which `fired:` already answers with what happened; `--format json` keeps the config. `first:` read as the first of something and meant the message before the shrink; it is now `  before shrinking: `. A script that matched `  first:  ` or `  config: ` in the human block must match the new label or read the JSON. GUIDE §8 also says `run` returns once nothing is left inside the horizon, as it does earlier in the section.
- **A check that tested nothing fails the batch, and a platform test in which every universe gave up fails.** A check whose every run was skipped printed `untested`, yet the batch exited 0, so a check that proved nothing read as a pass. A batch with an untested check now exits 1, with a `--filter` that selects only that check and at `--runs 1` too. Its result line says `FAILED`, or `nothing tested` when no check was tested. A line after the skipped runs' reasons names the fixes: raise `--runs`, change the setup until runs reach the check, or delete the check. A `--seed` replay of a skipped run still exits 0. `--format json` ends on two new keys, `result` (the result line's word) and `exit`. `run_universes!` and `run_universes_swarm!` (and their `_from`/`_with` forms) panic when every universe gave up, naming the test file and the universe count. Their seed derivation is unchanged. When the unmutated baseline is red because a check tested nothing, `charpente test --mutants` names that check. This reverses 0.3.0's "an untested batch still exits 0". GUIDE §8 "Giving up" and "Reading a batch" describe the new rule.
- **The shrinker deletes whole items, so a failure drawn as records of several draws shrinks to the records it needs.** Pass 1 deleted chunks of 8, 4, 2 and 1 choices, and none of those removes an item of three draws (a template, an acquirer and a target, say) at every position: a cut that was not one whole item shifted every later draw, and the run passed. In a probe with that record shape, 38 of 105 failures stopped above their minimum, keeping an item they did not need. After the chunks, pass 1 now deletes each run of choices from one draw to the next draw of the same name, when that run is two or more choices, and all 105 reach the minimum. For the same batch, a check whose items hold two or more choices can print a smaller shrunk run, another `--inputs` in its repro and another replay count, even when each of its draws is one choice: a bid drawn as a lab and an amount can shrink to the same run as before in one more replay. A check in which each draw's next draw of the same name follows it directly, a draw of one choice, shrinks exactly as before. A repro printed earlier still replays its run. GUIDE §8 "Shrinking a failure" describes the pass.
- **`charpente new` writes a `tests/sim.rs` driven by `charpente_sim::drive`, and a `src/lib.rs` whose `add_note` writes a note once: the same note again is answered as added, and the same id with another body is refused.** The generated sim no longer carries its own `open_app`, `run_kernel` and `recover`: each property runs `Drive::faulted_phase` and `Drive::recover`. A first boot lost to fault fallout now reaches the tail instead of giving the run up, the tail runs a minute so due jobs drain, and it re-sends every note the phase left unanswered. The event check reads the log with `checks::events::<NoteAdded>`, every page of it, where it read one `scan_from(0, 4096)`. A re-sent note may have landed the first time, so a repeat with the same body returns its id and enqueues and emits nothing; without that guard 5 of 256 runs at master seed 0x1 failed the echo check's exactly-once claim. A POST that reuses a stored note's id with another body is a conflict, refused with `400 note <id> already holds another body — a note is written once; post the new body under a new id`, where it used to overwrite the note. The echo check names a note added twice as the route's doing (`exactly-once violated: note <id> has <n> Echo jobs — it was added twice …`) before it blames the platform. Its ack check looks for each acked note's own `Echo` job, where it compared counts, so a re-sent note's job no longer makes up for an acked note's (`ack-durability violated: note <id> was acked with 200 but has no durable Echo job …`). The event check tells a missing `NoteAdded` (`event-durability violated: … is not in the event log — the emit did not commit with the row`) from one in the log more than once, which it names as the route's doing (`exactly-once violated: note <id> has <n> NoteAdded events — the route emitted it more than once …`). The same name renders different files, so a scaffolded app's recorded batches move.
- **Struct literals:** `HarnessArgs` gains `first_runs` (the quick pass, under Added), so a struct literal must add it, `first_runs: None` for a batch as before.
- **`charpente test --mutants` over an app runs two passes, and its report changes shape.** When a `--test-package` has a `sim_tests!` harness (`[[test]] name = "sim"`, `harness = false`), pass 1 judges every mutant under `CHARPENTE_SIM_FIRST_RUNS=32`, so only a failed run counts, and pass 2 judges what pass 1 missed or timed out at the full count, through cargo-mutants' `--iterate`. A quick pass's runs are a prefix of the full count's for every check, so each verdict is the one a single full pass gives, except that a mutant which fails an early run and then hangs is caught in pass 1 where a single full pass would time out. Before either pass the verb runs `cargo test` over the test set at the full count, so a baseline with an unmet `require` or an untested check exits 2 even when pass 1 leaves pass 2 nothing to judge. A test package without the harness runs in full in both passes; with none, the run is one full pass. Every process the verb starts gets one `CHARPENTE_SIM_MASTER_SEED`, and the verb's first line prints it. The report lists each mutant with its verdict and the pass that decided it (`(pass 1)`, `(pass 2)`, or `(one full pass)`), then the totals as before, a line naming the passes and the seed, a line naming the test packages judged at the full count, and last `rerun exactly this mutation run: charpente test --mutants <the flags given> --master-seed <seed>`. After a pass 2, `mutants.out` holds pass 2's record and `mutants.out.old` pass 1's. The verb's own `cargo test` runs (the full-count run and each timing run) print their output only when red, after a line naming the run, and a timing or full-count run red because a sim check tested nothing names the check, as cargo-mutants' baseline does. A test that spawns a sim under `--mutants` now also inherits `CHARPENTE_SIM_MASTER_SEED` and, in pass 1, `CHARPENTE_SIM_FIRST_RUNS`, under which an unmet `require` exits 0: remove both as `CHARPENTE_SIM_NO_SHRINK` is. GUIDE §8 "Two passes over an app, on one master seed" describes the run.

### Changed
- **`charpente test --mutants` refuses a relative dev-, build- or target-dependency path outside the workspace root, and names `TMPDIR` when the scratch copy runs out of disk.** cargo-mutants 27.1.0 rewrites relative paths only in `[dependencies]`, `[replace]` and `[patch]`, so a `[dev-dependencies]` entry such as `{ path = "../outside" }` failed the unmutated baseline in its scratch copy with "no matching package named `outside`", which the verb reported as a generic red baseline. The verb now reads the manifest of every workspace member (a member that is not a `--test-package` fails the copied baseline too), under either spelling cargo reads (`[dev_dependencies]` and `[build_dependencies]` included), exits 2 before the install check, and names the manifest, the table as the manifest spells it, the dependency and the fix (an absolute path, or `[patch.crates-io]`). A baseline log saying `No space left on device` now gets a line naming the temp dir and `TMPDIR`. GUIDE §8 says both.
- **The install-facing versions are 0.4.** `charpente new` writes `charpente = "0.4"` and `charpente-sim = "0.4"`, as GUIDE §1's manifest block does, and the six crates are 0.4.0.
- **The three shipped examples drive their app with `charpente_sim::drive`.** `restart_under_faults`, `drawn_inputs` and `modelled_remote` no longer carry their own boot, tail and clock wait: each runs `Drive::faulted_phase` and `Drive::recover`, so a first boot lost to fault fallout reaches the tail, and the tail re-sends what went unanswered (`drawn_inputs` merges the re-sent answers into its judgement). `modelled_remote`'s `place_order` answers an order that is already stored and enqueues no second charge, and its double-charge failure says whether the order was placed twice or re-called without a key. A rerun at an older master seed differs.

- **A `--seed` replay of a skipped run prints a `fired:` line.** Under its `skipped:` and `detail:` lines it shows the faults that fired in that run, rendered as a failure block renders them, so why a check skipped is readable without debug prints. A script that matches the replay's text exactly sees one more line.
- **`--faults-off` with a name that is not a fault axis lists the 26 axes.** It said only `"bogus" is not a FaultConfig field`. GUIDE §8 names them too.

### Added
- **`SimSource::answers()` returns one slot per `push_at`, in push order.** A slot stays `None` until its own request is answered, so a run that stops mid-source says which requests it never reached; `responses()` is unchanged. `Request` is now `Clone`, and `charpente-sim` depends on `charpente` (the recovery helper's groundwork).
- **`checks::events::<E>` and `checks::events_scoped::<E>` read the durable event log as the app's own event types.** In log order, every page of it, so no sim test decodes `EventRow` by hand; a row of another shape, or a payload that does not decode, is an `Err` naming the event, the row and the fix: read it with the type that wrote it.
- **`charpente_sim::drive` is the recovery every app that tests recovery under faults was pasting: a faulted phase, a power cycle and a fault-free tail, with answers per request.** `Drive::new(sim, build)` takes how the app builds itself. `faulted_phase(requests, horizon)` boots through fault fallout and runs the requests, given as offsets from the phase's start, under the run's faults; a request whose offset lies past `horizon` panics as a contract before anything runs, naming the last offset, the horizon and the fix (`raise the horizon past the last request, or space the requests closer`), because the phase would never send it; fault fallout ends the phase and is never a give-up or a skip, and a first boot that never gets past fallout gives an empty phase. `recover(phase, tail)` power-cycles, quiesces disk and clock faults (and outbound faults when the app declares hosts), waits out a clock refusal, boots, re-sends what went unanswered, and runs the kernel to `tail` past its boot, so due jobs, retries and cron drain. A request is re-sent when it has no answer, or a 5xx whose body is fault fallout; a 4xx or a handler's own 500 is the app's answer. Fallout is read from the body's text, so a handler's own 5xx whose message reads as fallout (`is_fault_fallout`) is re-sent too. The re-sent answers come back in `Recovered::resent`, apart from the phase's. `recover` returns `Ok(None)` only when the run gave up, on a durable refusal. Its errors are `the fault-free tail could not boot` (with `: <error>` when the boot failed with one) and `the fault-free tail's kernel stopped: <error>`. A clock refusal that outlasts two waits fails the run too, never a give-up: one wait always suffices, so `wait_out_clock_refusal`'s text says it is a platform clock defect and ends on the refusal. An app that declares a host the workload registered no model for gets `the app calls <host>, but the workload registered no model for it — call sim.remote("<host>", …) before Drive::faulted_phase`, not a panic.
- **`CHARPENTE_SIM_FIRST_RUNS` runs a quick pass, and `CHARPENTE_SIM_MASTER_SEED` pins a batch's master seed.** `sim_tests!` reads both at startup beside `CHARPENTE_SIM_NO_SHRINK`. A `--seed` replay ignores both, and a value the harness cannot read exits 2 naming the variable. `CHARPENTE_SIM_MASTER_SEED=0x…` sets the master seed when `--master-seed` is not given; the flag wins. `CHARPENTE_SIM_FIRST_RUNS=N` derives every check's seeds for the full `--runs` count, as a full batch does, and runs only the first N of each, so its runs are a prefix of the full batch's for every check. It judges failed runs only: it exits 1 when a run failed and 0 otherwise, and leaves `require` and the untested rule to the full count. Its rerun line starts `CHARPENTE_SIM_FIRST_RUNS=N`, its last line is `quick pass: the first N of each check's R runs, failed runs judged only — coverage and untested checks are judged at the full count`, and its JSON ends on `quick_pass` (`{first_runs, full_runs}`). It shrinks as a batch does unless `CHARPENTE_SIM_NO_SHRINK` is set. A count at or above `--runs` runs every seed, so that batch is a full one, judged as one, with no quick-pass line. `HarnessArgs` gains `with_env`, which reads the three variables through the lookup `sim_tests!` passes it. GUIDE §8 "Finding a one-sided property" describes both.
- **`charpente test --mutants` takes `--first-runs N` and `--master-seed 0x…`.** `--first-runs` sets pass 1's runs per check, 1 or more (default 32). `--master-seed` pins the master seed every sim batch in the run derives its runs from; without it the verb draws one and prints it. A value the verb cannot read exits 2 naming the flag.
- **`examples/api.rs` puts the API on one page.** It uses each attribute with every argument it takes, every `Tx` and `ScopedTx` method, the `App` builder with its `Schema` and its staged `Group`, `charpente::launch`, `Kernel`, `SimSource` and `Request`, the `Snapshot` reads, `sim_tests!` and the `run_universes` macros, `Sim` and `SimHost`, `FaultConfig`, `Input`, the remote models, `charpente_sim::checks` and `charpente_sim::drive`, each with its types and a comment that says only what the types do not. It compiles with the crate and ships in it, and GUIDE's opening points to it first. A census in `guide-examples` holds it. A new public function on one of those surfaces fails the census, naming the function and the file that defines it, unless the page's section for that surface already calls a function of the same name. A new word an attribute's parser accepts fails it until the page's attributes use the word, except `#[derive(Wire)]`'s serde words and `#[index]`, which the census header names as unheld. Agents building on 0.3.0 grepped the source to learn which methods exist.

### Fixed
- **`charpente test --mutants` no longer reads an earlier run's record as a pass's own.** When cargo-mutants died before moving the record in `--output` aside, the verb read the record already there, and reported a previous run's verdicts (or, in two passes, pass 1's quick verdicts tagged as pass 2's). The verb now notes the record's `start_time` before each pass and exits 2 when the record after it still carries that time, saying nothing was measured.
- **A `#[route]` handler in another module mounts whatever its visibility.** The marker struct inherited the handler's visibility, so `routes![handlers::x]` from the crate root hit E0603 on a struct the app never wrote. The marker is now `pub(crate)` for every handler narrower than that (private, `pub(self)`, `pub(super)` or `pub(in path)`), and `pub` for a `pub` handler; a `pub(crate)` handler's was already `pub(crate)`. The marker is inert, and the code that calls the handler stays in the handler's module. `#[job]` is unchanged: it sits on the app's own struct, where rustc's E0603 and its "make it pub" fix are right. GUIDE §5 says so.
- **An SSE route whose success type is an alias of `Subscription` is refused for what it is.** `#[route]` reads a handler's return type as written, before type aliases resolve, so `Result<Tail, ApiError>` with `type Tail = Subscription` was refused with "got a different return type", though the type was right. The refusal now says the macro reads the type as written, so an alias of `Subscription` is refused like any other type, and names the fix: `-> Result<Subscription, ApiError>` with `Subscription` itself. Any other mismatch, an alias of `ApiError` or of the whole `Result` among them, says the same and names the same fix. GUIDE §11 says so.
- **A job enqueued through a kernel's App between two runs of that kernel runs in the next one.** Only the end of a step that did work fed such an enqueue to the due-heap, so a `run` whose source held no request, with no schedule due, left the job Pending with no error. `Kernel::run` now feeds it before its first step. Production builds a kernel and runs it once, so a served app is unaffected.
- **An `Id<T>` of a type no `#[table]` declares names the fix wherever it crosses the wire.** rustc said only "the trait bound `X: Row` is not satisfied". `Row` now carries a note: declare the type with `#[table]`, or carry the id as a `WireU64` in a body, response or event field and as a `String` in a path param. GUIDE §5 no longer says that an `Id` of any `T` crosses the wire.
- **The `u64`/`i64` wire note names a fix that compiles in a path param.** It offered `WireU64`/`WireI64` there, which are not `FromParam`. It now names a `String` for a path param, and keeps `WireU64`/`WireI64` for a body, response or event field.

## 0.3.0 (2026-10-27)

### Breaking changes
- **`Clock` gains `wall()`; an implementor adds it.** `WallTime` is new.
- **Every stored or compared time is a `WallTime`; durations stay on `Instant`.**
  - Fields: `Session.expires_at`, `ApiKey.created_at`, `CronRow.next_due`, `JobRow.due_at` (`WallTime::UNIX_EPOCH` still means due now), `SessionSweep.before`, and `JobOutcome::Retried`'s `due_at`.
  - `App::handle_at`, `App::handle_or_subscribe` and `StagedDispatch::stage_or_subscribe` take `now: WallTime`. `App::handle` passes `WallTime::UNIX_EPOCH`.
  - `OidcVerifier::verify` takes `now: WallTime`.
  - `CronEnqueue` is `Box<dyn Fn(&mut Tx, WallTime) + Send>`. `CronScheduler::upsert`, `tick`, `tick_into` and `has_due` take a `WallTime`, and `next_deadline` returns one.
  - `Dispatcher::run_due` and `run_due_into` take the new `kernel::Now`, one reading of both clocks: `mono` times an outbound call's deadline and `wall` judges due times. `Dispatcher::has_due` takes a `WallTime`, and `next_deadline` returns one.
  - The fingerprints of the platform tables `Session`, `ApiKey` and `CronRow`, and of the platform job `SessionSweep`, change with their field types.
- **A 0.2 data directory, replication peer or archive bucket is refused by name, with the fix in the text.** Nothing is migrated (DECISIONS §15).
  - A data directory whose platform table (`Session`, `ApiKey`, `CronRow`) has another shape: start from an empty directory or restore a 0.3 archive.
  - `PROTO_VERSION` goes from 6 to 7: a 0.2 peer is refused at Hello; replace it with a fresh follower.
  - `Manifest` gains `format`, and `MANIFEST_FORMAT` is 3: `restore` and archive adoption refuse a manifest with another format, or none; archive to a fresh bucket prefix.
- **`CronRow.interval_nanos` is the interval the row's `next_due` was set with.** `CronScheduler::upsert` no longer rewrites it on an existing row; the next tick writes it with `next_due`.
- **The simulator's clock axes.** `FaultConfig` gains `clock_skew`, `clock_step_back` and `clock_downtime`: an exhaustive literal breaks, and `..FaultConfig::none()` still works. `checks::FaultReason` gains `ClockRefused`, so an exhaustive `match` over it must handle it.
- **`run_universes_swarm_with!`'s `adjust` takes the universe's seed: `|seed, cfg| …`, not `|cfg| …`.** A value an adjust draws comes from a stream keyed by the seed, so a change to `FaultConfig` no longer moves it. An adjust that ignores the seed draws nothing new, and no platform suite's pinned seed moved.
- **`Sim::give_up` takes a fixed reason and a per-run detail: `give_up(reason: &'static str, detail: impl Display)`.** A batch counts each check's skipped runs by reason, and the detail is that one run's own text. Split a text that embeds an error, count or seq into its fixed part and the detail; a fixed reason passes `""`, and an empty detail is none. `Sim::gave_up()` returns `Option<&'static str>`, `Sim::gave_up_detail()` returns `Option<String>`, and `Outcome::GaveUp` is `{ reason: &'static str, detail: Option<String> }`. A batch prints the reasons; replaying the run with `--seed` also prints its detail.
- **`charpente test --sim --universes N` is `--runs N`.** `--universes` is an unknown flag and exits 2, and `HarnessArgs.universes` is `HarnessArgs.runs`. Nothing keeps the old name: change every script that passes it.
- **Struct literals:** `HarnessArgs` gains `inputs`, `faults_off` and `no_shrink`, and `UniverseEnd` gains `choices` and `drawn`. `harness::Failure` gains `drawn` and now has crate-private fields, so it can no longer be built by a struct literal or destructured without `..`.
- **A session minted through `App::handle` has already expired when a kernel presents it.** `App::handle` judges at `WallTime::UNIX_EPOCH`, so the session's `expires_at` is `session_ttl` after 1970; under 0.2 it lived for `session_ttl` (30 days by default) of uptime. No compile error flags this. Mint a credential a kernel will see through the kernel, or call `app.handle_at(request, clock.wall())` with the node's clock (GUIDE §5).
- **`charpente test --sim --format json` has a new shape.** Keys in order: `master_seed`, `runs`, `passed`, `failed`, `skipped`, `coverage`, `missing_coverage` (`{check, key}`), `checks` and `failures`. Each of `checks` is `{check, status, passed, failed, skipped, distinct_inputs, drew_inputs, skipped_reasons}`, with every skipped reason as `{reason, count, first_seed}` and a `detail` under `--seed`. Each of `failures` is `{check, seed, config, fired, message, inputs, faults_off, first_message, not_shrunk, replays, repro}`: a check's first failure carries its shrink (or, with shrinking off, `not_shrunk`), and every other is its own unshrunk run with a repro that is its seed alone. `universes`, `verdicts`, `gave_up`, `outcomes`, `summary`, `test`, the per-failure `master_seed` and `coverage` are gone: read `runs`, `passed`, `skipped`, `checks`, `check` and `fired`. `Report::to_json` is gone with them. Under `--seed` the first key is `seed`, not `master_seed`, followed by `inputs` and `faults_off` when the replay was given them: the replayed seed fed back as `--master-seed` would run another batch.

### Changed
- **README's "Try it" ends on the pitch: delete `tx.enqueue` and `acked_post_implies_the_echo_after_recovery` goes FAILED with inputs shrunk to a run no shrinking step can make smaller, and a replay command. The `charpente new` scaffold declares `rust-version = "1.99"`, and GUIDE §1's manifest block matches it.** So do the six published crates, through `[workspace.package]`, so `cargo install charpente-cli` on an older toolchain gets cargo's own refusal by name. The install-facing versions (`charpente new`'s `"0.3"`, GUIDE §1) are 0.3.
- **Replaying one seed (`--seed`) prints each check as `ok`, `FAILED` or `skipped`, and a skipped run's reason with its detail.** It ends with `sim result: {word}. {p} passed; {f} failed; {s} skipped, on seed 0x…`, plus `with the given inputs` or `with faults off: …` when `--inputs` or `--faults-off` was given.
- **`--filter S` selects the check named exactly `S` when there is one**, and otherwise every check whose name contains `S`, as before. `charpente test --sim`'s usage text says so. A failure's repro line, `--filter {check} --seed 0x…`, now replays that check alone when another check's name contains it, instead of feeding its `--inputs` to both.
- **The skipped-run coverage key `universe:gave-up` is `run:skipped`.** A `ceiling:` or `require:` naming the old key stops matching: rename it. The app-facing text (GUIDE, README, `charpente new`) says run, check, tested and skipped throughout.
- **`charpente test --sim`'s batch output is one an agent can act on.** A failing check prints one failure block, its first failure shrunk, and its check line counts the rest. Then come the skipped runs' reasons with their counts (eight per check, the rest counted), each with the seed of its first run (`(first: --seed 0x…)`), which `--filter <check> --seed` replays, and the checks that draw no inputs, named. The output ends on a line per check in `cargo test`'s shape, `ok`, `FAILED` or `untested`, with how many runs tested it, over how many distinct inputs when it draws any, how many failed and how many were skipped, then a result line (`ok`, `FAILED`, or `nothing tested` when every check is untested) and the command that reruns exactly the batch. The result line gives each check's tested runs again, in the order of the check lines (`Runs tested per check, in the order above: 209, 251, 214 of 256.`, or `Runs tested: 251 of 256.` for one check), and no total across checks, which would let a barely tested check hide behind well-tested ones. So the last lines of the output carry every check's counts beside the verdict, as `cargo test` ends on its per-test lines and `test result:`. The startup line on stderr names the checks, the runs and the master seed. The human output is for reading; `--format json` is the parsed format, and it still lists every failure. See GUIDE §8 "Reading a batch".
- **The `charpente new` scaffold's sim draws its inputs and proves the event.** It posts 1 to 4 notes whose bodies and order come from `sim.input()`, so a failure shrinks toward the fewest, simplest notes, to a run no shrinking step can make smaller. A third check, `acked_post_implies_its_event_after_recovery`, requires each acked note's `NoteAdded` in the durable event log exactly once after recovery, so deleting `tx.emit` now goes red. The scaffold's recorded batch moves (named step S4).
- **`checks::acked_implies_durable`'s give-up names the round count as its detail** (`3 rounds`), not as nothing.
- **Cron keeps its grid.** A tick advances `next_due` to the schedule's next grid slot, `next_due + interval * ((now - next_due) / interval + 1)`, not to `now + interval`, so a late tick no longer drifts the phase. Catch-up still fires once.

### Added
- **Under `charpente test --mutants` an app's sim does not shrink.** The verb sets `CHARPENTE_SIM_NO_SHRINK=1` on cargo-mutants and on its timing run, and `sim_tests!` reads it into the new `HarnessArgs::no_shrink`. A failing check then prints its first failure as it ran, its `shrunk:` line saying it was skipped and why, and its repro replays that run; the batch's rerun line starts `CHARPENTE_SIM_NO_SHRINK=1`, so pasted it prints that report again. A caught mutant costs about its green baseline, since no shrink is added, where a shrink of up to 500 serial replays outran cargo-mutants' five-times timeout and read TIMEOUT. A test that spawns a sim and asserts on its shrink removes the variable from the child's environment.
- **`charpente test --mutants` names every function in which no mutant was viable.** Below its totals it lists them by file as untested, with what to do: a function whose every mutant failed to build (often because cargo-mutants cannot build a value of its return type) was never measured, and "0 missed" said nothing about it. The exit status is unchanged. GUIDE §8 says what cargo-mutants generates.
- **`charpente --version` (and `-V`) prints `charpente {version}`.** Any other unmatched argument prints usage on stderr and exits 2; the usage gains `usage: charpente --version`.
- **Wall time never runs backwards within a node.** The kernel holds its wall reading at the latest value it used when the clock steps back by up to `CLOCK_TOLERANCE` (60 s), and stops by name, with both fixes in the text, beyond that. It also stops by name (`clock stalled: …`) when its clock has read at or behind the held value for more than the tolerance since that value last rose, so a clock that stops advancing stops the node instead of holding sessions open and schedules still. Each hold episode, a step back or a freeze, costs at most the tolerance before a named stop. A clock that runs slow, and steps within the tolerance adding up, pass every check and drift against other clocks (an identity provider's, another node's): keep NTP on. A node opening, whatever its role, or being promoted, is refused by name while its clock is more than the tolerance behind the latest time its data directory recorded (an API key's `created_at`, a schedule's last tick or its creation); a switchover's target completes the hand-off and its kernel stops with the same refusal. Each refusal names the instant after which the node will open (or, for a refused promote, can be promoted); a hand-off's target says it will open, since its role has flipped and the restart opens it. See GUIDE §7 "Clock errors".
- **The simulator models wall time and its faults.** A clock's `wall()` is `Sim::true_wall()` (virtual time plus 2026-01-01T00:00:00Z) plus its offset, and `SimHost::clock()` gives each host its own. Three axes act on the offset: a skew each clock draws once, within ±`clock_skew` (up to 120 s), a step back of up to 120 s at a wall read, and a forward jump of up to three days at a power cycle (downtime). Each clock's skew, steps and jumps draw on streams of its own, so two hosts' clocks disagree, and the steps and jumps compound over a run; `SimClock::offset` reads a clock's offset without drawing. `charpente test --sim` turns each on in a quarter of runs, and they mark `clock:skewed`, `clock:stepped-back` (with `:within-tolerance` or `:beyond-tolerance` by size) and `clock:downtime` when a reading shows them. The platform's own suites leave them off, so none of their pinned seeds moved. `checks::clock_refused` names the kernel's clock stops and its open/promote refusal; `checks::clock_fallout` excuses one only where a clock axis acted in the run, and `is_fault_fallout` never does. `Sim::quiesce_clock_faults` freezes every clock's offset for a fault-free tail, which waits out a refusal until the instant it names (`checks::clock_reopens_after`; `None` for the stall stop, which names none). See GUIDE §8 "Wall time and its faults".
- **`sim.input()` draws a workload's inputs from their own stream and records them.** `between`, `pick`, `shuffle` and `text` each record the choice they used: the stream's raw `u64` reduced into the draw's range, the smallest raw value that draws the same value. So a choice and its value are one to one, a smaller choice is a simpler value (`lo`, the first item, identity order), and a run's `choices` and `drawn` (each input by name) come back on its end or failure for the harness to replay and shrink. Drawing moves no fault draw. See GUIDE §8 "Drawing inputs".
- **A failure shrinks to smaller inputs and fewer fault axes that still fail its check.** `charpente test --sim` replays each check's first failure in a batch, in seed order, with smaller input choices (equal ones also lowered together, so a failure that needs the same entity drawn twice reaches the lowest one) and with each fault axis that was on turned off, and keeps each smaller run that still fails the check, with any message. When a round of its passes keeps nothing it ends on a local minimum, a run no step of its passes shrinks, not on a search of every smaller run. Its budget is 500 replays, counted, never timed, so the result is the same for any `--jobs`; a shrink that spends it stops with the smallest run found so far, which can be short of a local minimum. The failure block gains `inputs:` (each draw by name), `shrunk:` (draws before and after, the axes turned off, the replays) and, when the shrunk run failed with another message, `first:` with the original; its headline, `config:` and `fired:` are the shrunk run's, and its repro replays exactly that run. Two new flags, both requiring `--seed`, carry it: `--inputs HEX` (each choice as LEB128, in lowercase hex) and `--faults-off AXIS,…` (`FaultConfig` field names). A `--seed` replay shrinks nothing. In `--format json` a check's first failure is its shrunk run, and every other failure is its own unshrunk run. See GUIDE §8 "Reading a failure, replaying its seed" and "Shrinking a failure".
- **GUIDE ships inside the `charpente` crate, with three compiled sim examples.** `charpente::guide` is the guide's page on docs.rs, and the registry copy carries `GUIDE.md`. Each of `drawn_inputs`, `modelled_remote` and `restart_under_faults` is a whole `tests/sim.rs`: in an app, copy one there and run `charpente test --sim`; in a charpente checkout, `cargo run -p charpente --example drawn_inputs` runs it, with flags after `--`. GUIDE §8 "Examples to copy" names them.
- **`checks::wait_out_clock_refusal(sim, boot)` is a fault-free tail's boot loop.** It calls `boot` and, when it fails with a clock stop or refusal this run's clock faults explain that names an instant, sleeps one second past that instant, restarts the process and boots again, twice at most; a third refusal fails the run as a platform clock defect, never a give-up, since one wait always suffices and a skip would hide it. The scaffold, the three examples and GUIDE §8's worked tail use it instead of five copies of the loop. `charpente_sim` re-exports `OutboundCall` and `OutboundReply`.

### Fixed
- **A `require`d key that failing runs reached has occurred.** A batch counted only passed and skipped runs' coverage toward `require`, yet said the key `never occurred in <n> runs`, every run, and advised dropping the requirement. A failed run's coverage now counts too, toward `require` and in `--format json`'s top-level `coverage`, in a batch and under `--seed`, less its `run:skipped`: a run that gave up and then failed is a failure, so `run:skipped` still counts skipped runs exactly. A green batch has no failed runs, so its output is unchanged.
- Production time was process uptime, so after a restart or failover cron stalled until uptime caught up, sessions outlived their TTL, an expired OIDC token was accepted and any token with nbf was refused. Every stored or compared time is now wall-clock time (WallTime).
- **`CronScheduler::tick` and `Dispatcher::run_due` no longer undo in-memory state for a commit whose record reached the store, and `CronScheduler::upsert` follows the same rule.** Before, after a checkpoint failure that nothing else reports (the horizon breadcrumb's sync, which poisons and latches nothing), `tick` rolled its schedule back and re-enqueued an interval the store already held on its next call, `run_due` put a Done job back in its heap and panicked on its next call, and `upsert` left a new schedule's cache at `UNIX_EPOCH`, so it ticked at once. All three still answer `Err` there. These are the wrappers tests call directly; the kernel's own cron and job arms always stopped on a commit failure, and every production caller of `upsert` propagates its `Err`.

## 0.2.0 (2026-10-17)

### Added: outbound effects
A job declared `#[job(outbound = "<host>")]` can call an external service: email, a payment API, an LLM.
- Its `call` is read-only and decides the request. The kernel then makes the request outside any transaction, through the `Outbound` IO trait.
- Its `settle` commits the reply's consequences and the job's Done-mark as one record.
- Every outbound job carries an idempotency key the platform mints from `Entropy` when the enqueue is staged.
- The simulator injects outbound faults: lost requests, lost replies, slow replies, throttling (a 429 or 503) and refused connections. `charpente_sim::checks` gains `calls_have_durable_jobs`, `keys_are_per_job` and `outbound_settles_by_horizon`.
- Production calls go through a hyper + rustls (`ring`) client at the edge, configured by `OutboundOptions` through `serve::serve_with` and by the `--outbound-base`/`--outbound-ca` flags.
- See GUIDE §6 "Outbound jobs: calling the world after commit", §8 "Calling the outside world in a sim", §13 "Outbound jobs and hosts in the contract", and DECISIONS §14.

### Breaking changes
- **`JobOutcome` gains `Calling`.** An exhaustive `match` over it no longer compiles until it handles the new variant. That is deliberate: charpente keeps its public enums exhaustive so that a new outcome is a compile error, not a silent wildcard.
- **Struct literals:**
  - `JobDef` gains `outbound`.
  - `JobRow` gains `outbound_key`.
  - `KernelStats` gains five fields: `outbound_started`, `outbound_settled`, `outbound_failed`, `outbound_timed_out` and `outbound_late`.
  - `FaultConfig` gains six outbound fields: `outbound_refused`, `outbound_lost_request`, `outbound_lost_reply`, `outbound_throttle`, `outbound_slow` and `outbound_latency`. An exhaustive literal breaks; `..FaultConfig::none()` still works.
  - `describe::Contract` gains `outbound_hosts`, and `describe::JobInfo` gains `outbound`.
- **Signatures:**
  - `Db::drain_enqueued` returns `Vec<Enqueued>` instead of `Vec<Id<JobRow>>`, and `Dispatcher::note_enqueued` takes it.
  - `table::Writer::materialize_job` gains an `outbound_key: Option<[u8; 16]>` parameter.
  - `Db::register_job_shapes` takes a 4-tuple; the new fourth element is the job's outbound host.
- **Replication:** `PROTO_VERSION` goes from 5 to 6, so a 0.1 node and a 0.2 node refuse each other at Hello. Upgrade the way GUIDE §12's "The upgrade procedure" describes, with both nodes stopped.
- **Downgrade:** unsupported once an outbound job has been enqueued. A 0.1 binary refuses the outbound enqueue record as an unknown effect tag, and reads a job row that carries an idempotency key as corrupt.
- **Refusals that are new or reworded** (error text is product surface):
  - An enqueue whose `Job::OUTBOUND` (a new associated const, `false` by default) contradicts the mounted `JobDef` is refused at enqueue, by name, before any key is drawn (new). Only a hand-written `impl Job` or `JobDef` can reach it.
  - The `Db::register_job_shapes` panic for a job registered with two declarations now also says, for each, whether it is a pure job or `outbound = "<host>"`.
  - The `enqueue_keyed` empty-key panic now calls the key an `enqueue_keyed` app key, not an idempotency key.
  - The `#[job]` argument errors that quote the accepted forms now list `outbound = "<host>"` and `timeout` among them.
  - An app whose jobs call no host refuses to start when given `--outbound-base`, or an `--outbound-ca` file that cannot be read or holds no PEM certificate. 0.1 had neither flag and rejected both as an unknown verb.
  - The new outbound compile errors and contract panics are listed in GUIDE §9.
- **Output formats:**
  - `describe --format human` gains ` outbound=…` on each job line and an `outbound_hosts:` section.
  - The JSON gains `outbound` on each job and a top-level `outbound_hosts`.
  - A sim failure's `config:` line gains the six new `FaultConfig` fields.
  - `LAUNCH_USAGE` gains a third line for the serve form's outbound flags.
- **Tooling skew:** a 0.2 CLI's `gen-client` cannot read a 0.1 app's `describe` output, because it requires `outbound_hosts`. Upgrade the CLI and the app together.
