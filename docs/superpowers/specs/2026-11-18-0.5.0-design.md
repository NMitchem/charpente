# 0.5.0 — what apps build because the platform does not

**Date:** 2026-11-18. **Status:** approved by Noah 2026-11-19. Written from Noah's direction of
2026-11-18: run 0.5.0's spec in parallel with the launch demo's rehearsal, and add a delayed
enqueue to the three named rows "if B lines up with the manifesto" (§9 records the reading). He
handed over the approach. The controller's calls are marked as such in §9.

A builder check on 2026-11-18 asked nine questions and found seven claims the code contradicted or
left materially incomplete. The controller verified each one against the source. Eight questions
were settled from rules this document or the repo already states, and §5 and §7 now carry the
answers. The ninth (the small-API-gaps row) is Noah's. The ground truth is
`.superpowers/sdd/2026-11-18-0.5.0/recon.md` and `builder-check.md` (local).

## 1. Why

PLAN names 0.5.0 (PLAN.md:283-288) and marks three rows "Due, named for 0.5.0" (PLAN.md:360-362).
Each one is a place where an app keeps a second copy of something the platform already holds.

- **A clock row beside the platform's clock.** invoicing (`AppClock.day`, FINDINGS.md:9-42),
  helpdesk (`AppClock.hour`, FINDINGS:73-78), statuspage (FINDINGS:372-373), agents A and C on
  0.3.0 (0.4.0 spec:149-150), and holdqueue on 0.4.0 all built a cron-advanced counter, because a
  transaction has no time (GUIDE:2751). That clock lags by every downtime. holdqueue's 7-day hold
  expiry fires late by that much (review T13; GUIDE:2757-2761).
- **A watchdog over a queue the app cannot read.** A Dead job is invisible to its app (`JobRow` is
  `PlatformOwned`, job.rs:114-122; no hook fires). Agent C's watchdog and redrive came to about a
  third of its jobs code (0.4.0 spec:145-147). holdqueue's ready notification goes Dead after
  about 68 minutes of notify outage, and the patron is never told (review I5).
- **A redrive that sends a second key.** The minted key covers one job, so C's redrive sent the
  effect twice to a remote that honours keys. C planted that double fire and the sim caught it
  (PLAN.md:362).
- **A timed obligation stored as a row plus a sweep.** Every enqueue is due at once. holdqueue
  asked to "run this job at time T" (FINDINGS:22, :47; review T4).

The launch demo is the consumer. Its §9 step 4 says "a task with timed emails needs both time and
a visible Dead", and its public attempt waits on this publish
(2026-11-06-launch-demo-design.md:340-345).

The manifesto reading: one commit point (MANIFESTO §5) is the deletion of the dual-write class
(§4). A clock row, a watchdog, and a row-plus-sweep are each an app-side copy of platform state,
kept consistent by hand. 0.5.0 puts each one back in the transaction that already owns it.

## 2. What exists today

The facts the design rests on, with citations at `392b03ca`.

**Time**

- `Clock` has a monotonic `now` and a `wall` (io.rs:137-144). The kernel reads both once per step
  (`Now`, kernel/mod.rs:457-460), and every kernel arm already holds that step's `Now`
  (mod.rs:780, :909, :1009, :1149, :1158). `Tx` and `Group` hold no time (db.rs:1235-1249,
  :3641-3651).
- The wall half passes a hold that never runs backwards within a process. At open and promote it
  is floored by a bound recovered from stored times, namely the newest `ApiKey.created_at` and
  each `CronRow`'s `next_due - interval` (DESIGN.md:99-121; clock.rs:123-135).
- A handler reads no time (GUIDE:725-726, :2745-2747). DESIGN §2, an [IRREVERSIBLE] section,
  already says a transaction "gets the transaction's logical timestamp" (DESIGN.md:519-520).
  Nothing implements it.
- **The log stores effects, not commands** (2026-07-02-transactions-design.md:30-32;
  db.rs:8-24). Recovery and followers never re-run a closure.

**Enqueue**

- Apply hard-codes a new job's `due_at` to `UNIX_EPOCH` (`materialize_job`, table.rs:1627-1661),
  and `Effect::Enqueue` has no due field (db.rs:719-728).
- The kernel learns of fresh jobs through `Db::drain_enqueued` → `Dispatcher::note_enqueued`
  (mod.rs:1232-1234), which queues every one as due now (dispatch.rs:336-346).
- `Enqueued` carries `{id, outbound}` (db.rs:2559-2568) and is fed from the record, never a store
  read, because "a read would draw sim fault rolls and re-roll every universe" (plan amendment
  A8). Only `Dispatcher::rebuild` reads a row's `due_at` (dispatch.rs:315-334), and it runs at
  kernel start and when the write gate opens.
- `enqueue_in` already exists and means "into another tenant" (db.rs:1546).

**Dead**

- `JobStatus` is `Pending | Done | Dead` (job.rs:13-39). Dead is set in `stage_failure_record`
  (dispatch.rs:1157-1211). That is a single `group.stage` closure whose error type is `io::Error`,
  and any `Err` from it stops the kernel (dispatch.rs:1181-1210, :584-587, :846-849).
- It runs no app glue and builds no `JobScope`. Every path to it stages into a group that mints
  (app.rs:752-758). Only `run_due_into` mints the `CrossTenant` capability (dispatch.rs:453).
- The run path reclassifies three refusals as attempts: `JobShapeRefusal` and
  `TableWriteRefusal` arrive as `TxError::Io`, and `TableReadRefusal` as `JobError::Io`
  (dispatch.rs:529-549; settle's copy at :1006-1017).
- An unregistered name goes Dead with no glue. `JobError::Io` and a crash are never attempts.
- The public one-job `Dispatcher::run_due` stages into a group that cannot mint (dispatch.rs:627).
- `#[job]` already folds `outbound` into `FINGERPRINT` (macros job.rs:8-12).

**Keys**

- 16 bytes are drawn from `Entropy` at staging, only for an outbound enqueue. The minting loop
  writes `okey` for every outbound enqueue in the group (db.rs:4866-4882).
- `IdempotencyKey::from_bytes` is public (io.rs:334). `keys_are_per_job` fails whenever two rows
  share a key (checks.rs:657).
- DECISIONS §14: keys are platform-minted because keys derived from ids collide across the loss
  window (DECISIONS.md:429-431). The `Idempotent` model answers a reused key with different
  parameters with a 409 (GUIDE:2201-2208).

**The log and the wire**

- Record kinds `0x00`-`0x0d` are in use, and `0x0e` is the next free one (db.rs:8-24). An unknown
  kind is refused by name (db.rs:1076-1084).
- `PROTO_VERSION` (7) bumps for a new kind (repl/mod.rs:40-56). `MANIFEST_FORMAT` "tracks the
  charpente minor" (archive/manifest.rs:89-93), and DECISIONS §15 names it as the bucket's
  detector.

**The sim and Dead**

- No outbound job reaches Dead under drawn faults: 0 in 499 universes in the outbound build
  (attempt-1 review.md:186-190). A pure job does reach Dead through its own deterministic failure
  (charpente-sim tests/drive.rs:569-593), and scripted platform suites reach outbound Dead.
- The causes: per-call independent faults at low rates, no outage axis, a scaffold faulted phase
  of 2 s (templates/sim.rs.tmpl:84-85), and a tail that quiesces every outbound roll
  (drive.rs:253-256; sim outbound.rs:9-10). Default retry is 5 attempts with a 30 s doubling
  backoff (job.rs:50-53), plus a 30 s default timeout.
- Extended and clock axes draw from their own keyed streams. `FaultConfig::swarm`'s six axes are
  sequential ("do not reorder", lib.rs:216-305).
- The config is sampled before the app exists (lib.rs:3043-3066), so it cannot know the app's
  hosts. The clock axes are sampled app-only "so no pinned platform seed moves either"
  (lib.rs:487-517).
- `outbound_settles_by_horizon` fails on any Pending outbound row, whatever its `due_at`, and
  takes only a `&Snapshot` (checks.rs:679-698).
- A property judges lateness against `sim.true_wall()` (lib.rs:1300-1302). The kernel cannot
  reach the `Sim` (it never calls `sim.cover`), and `KernelStats` resets with every kernel.
- Drive builds a new kernel for its tail (drive.rs:257).

## 3. Goals, non-goals, anti-goals

**Goals.**

1. A transaction reads its time: `tx.now()` on `Tx` and `ScopedTx`.
2. A job can be enqueued to run at a time.
3. Every job declares what its Dead means. A declared hook runs in the transaction that commits
   the Dead mark.
4. A redrive from that hook resends the same request under the same key.
5. An outbound job reaches Dead in the sim under a drawn provider outage, and an app can require
   that its Dead path ran.
6. GUIDE §7's hand-built logical clock is retired in favour of goals 1 and 2.

**Non-goals.**

- **R3's stored wall reading** (PLAN.md:370). It keeps its row, and its trigger widens (§5 A).
- **An arbitrary caller-chosen key.** DECISIONS §14 stands.
- An app-side job cancel, an app reading `JobRow` (PLAN.md:351's row), a backoff cap, and Dead
  for `JobError::Io` or a crash loop.
- **Gating `charpente.jobs`** (R6, PLAN.md:371). It isn't triggered, because nothing here changes
  `JobRow`.
- **A new edge-harness failover vehicle.** See §7.4.
- **The small-API-gaps row** (PLAN.md:385; its trigger is met). It is Noah's call (§9).

**Anti-goals.** Each of these would be a failure even if everything technically works:

- A hook whose effects commit anywhere except the Dead mark's own record.
- `tx.now()` reading a clock from inside a transaction, or two runs of one seed seeing different
  times.
- A default for the Dead stance: a macro fallback, a config key, or a builder default
  (DECISIONS §13).
- A re-issue that accepts an `IdempotencyKey` value, or sends a different request under the dead
  job's key.
- The stance folded into `FINGERPRINT`. That would change every job's recorded shape, make every
  0.4.0 data directory with a Pending job refuse to start, and break SessionSweep's rule
  (auth/sweep.rs:25-30).
- A pinned seed or recorded batch moving outside §4's named steps.
- A `JobRow` change. It would fire DECISIONS §15's detector rule and R6's cost. If the build finds
  it needs one, it stops and raises it.

## 4. Constraints

- **Hard rules 1-6** as written in CLAUDE.md. In particular: every new output line and refusal is
  pinned against its exact text (5); GUIDE, CHANGELOG and examples change in the commit that
  changes the behaviour (6); each defect gets its failing test before its fix (3).
- **Determinism.** These steps move recorded output on purpose. Each is named, lands once, and
  records its before and after:
  - (a) **The outage axis is sampled app-only**, as the clock axes are, so no platform swarm
    suite and no platform-pinned seed moves. It is keyed, not sequential. In app batches:
    - universes where it is drawn on move, in apps that declare hosts;
    - in a hostless app's failing universe where it is drawn on, the shrinker spends a replay
      turning it off, so the `faults off:` line, the repro's `--faults-off` and the replay count
      change.
  - (b) `FAULT_AXES`, the `--faults-off` valid-axes refusal (cli.rs:241-247), and the frozen-copy
    test (lib.rs:519-524), which "turns red by design" on a new axis.
  - (c) `--format json` output, whose config gains the axis.
  - (d) `describe` JSON and its goldens, which gain each job's Dead stance.
  - (e) The re-pinned texts of `outbound_settles_by_horizon` and the per-effect key checker.
  - (f) Any example or scaffold whose recorded output changes because it adopts goals 1-5.

  Nothing else moves:
  - A log with no delayed enqueue and no re-issue is byte-identical to today's.
  - No new code path draws `Entropy` or a sim roll unless it is used. That is outbound invariant
    6's precedent (outbound spec:191-193), and amendment A8's rule that the dispatcher learns of
    jobs from the record.
  - Two runs of one batch, and runs at `--jobs 1` and `--jobs N`, still print byte-identical
    output.
- **Formats.** `PROTO_VERSION` and `MANIFEST_FORMAT` both bump, because the WAL gains record kinds
  and DECISIONS §15 wants a 0.4.0 node or restore refused at the detector, not late at replay. A
  0.4.0 node opening a 0.5.0 data directory is refused by the existing unknown-kind text.
- **No compatibility** (Noah, 2026-10-22). Making the Dead stance required breaks every `#[job]`
  in place. CHANGELOG lists it.
- **Version:** 0.5.0 for all six crates, and `charpente new` writes `"0.5"`.
- **Dependency edges** inside the deterministic boundary stay as they are, unless the plan states
  a reason.
- **Numbers.** docs/BENCH.md is the only source of quotable performance numbers.

## 5. The parts

### A. `tx.now()`

- **What it returns.** The step's held wall reading, `Now.wall`: the same value the dispatcher
  and session code use for that step. Its type is `WallTime`. It is available on `Tx` and
  `ScopedTx`, so on every route, job, cron-enqueued job and Dead hook.
- **How it gets there.** A time field on the group or `Tx`, set by each kernel arm from the `Now`
  it already holds. No record byte changes.
- **A `Tx` outside the kernel** (`Db::transact` in operator or test code). It may get a time only
  from a time its caller passes explicitly. A `Tx` with no time source fails to compile or is
  refused by name. It never reads zero or the epoch.
- **What it promises.**
  - Every transaction in one step sees the same value, and it never runs backwards within one
    process.
  - Across a restart or failover, a node whose clock is behind opens unnoticed if it is behind by
    less than DESIGN §1's recovered bound. That bound is the time since the store's newest
    recorded time (an API key's creation, or a schedule's last tick), plus `CLOCK_TOLERANCE`.
  - For an app with no API keys and no schedule of its own, that leaves the platform's daily
    session sweep, so the bound is about 24 h plus the tolerance.
  - GUIDE §7 states that number, says that a timed obligation can then run late by up to that
    much (never early in the node's own frame), and says that a frequent schedule tightens it.
  - R3's row (PLAN.md:370) widens its trigger to "an adopter whose timed obligations, or whose
    sessions, must not run late across a backwards clock step at restart".
- **The log does not change.** Replay applies effects, so a time a closure read only matters
  through what it wrote. In the sim, the reading is virtual time passed through the same hold, so
  the clock axes (GUIDE:3562-3576) reach `tx.now()`.
- **On a follower,** a read path that offers `tx.now()` uses the follower's own held reading, as
  session expiry does today (DESIGN.md:111-113).
- **Docs.** DESIGN §2's promise becomes true, and DESIGN §1 gains the bound sentence. GUIDE §7's
  logical-clock section is rewritten around `tx.now()` and part B, and "There is no platform
  primitive" goes. `App::schedule`'s `make` does not gain the tick time, because the job reads
  `tx.now()`.

### B. Delayed enqueue

- **The API.** An enqueue that names a due time, either absolute (a `WallTime`) or relative to
  `tx.now()` (a `Duration`), on `Tx` and `ScopedTx`. Proposed names are `enqueue_at` and
  `enqueue_after`, never `enqueue_in`. The builder decides the keyed and cross-tenant variants by
  what the existing family needs. A past time is due at once.
- **The path the due time takes:**
  - a new enqueue record kind (`0x0e`, plus its scoped and outbound forms as needed) carries it;
  - `materialize_job` takes it and writes it to `JobRow.due_at`;
  - `Enqueued` carries it from the record;
  - `note_enqueued` queues the job at that time.

  It is never a store read (amendment A8). `JobRow` is unchanged. `JobRow.due_at`'s doc
  ("every enqueue writes it, and only a retry moves it", job.rs:81-83) and DESIGN:96's wake-up
  sentence change with it.
- **Running.** The dispatcher runs the job when the node's wall reaches the due time. A job that
  falls due while the node is down runs once at recovery, late by the downtime.
- **Outbound jobs.** The key is minted at staging, which is enqueue time. At dispatch, `call` reads
  committed state and may decline, and a declined job is Done. That is how a cancelled booking's
  reminder never sends. GUIDE shows this pattern, and it says there is no cancel API.

### C. The Dead stance and its hook (DECISIONS §13)

- **Required choice.** Every `#[job]` declares one of two named alternatives:
  - a hook, which requires an `on_dead` method;
  - an explicit "retain", which is today's behaviour: the row is kept with `last_error`, and
    nothing runs.

  Leaving it out is a compile error naming both, with its compile-fail pin and its GUIDE §9 line.
  The spelling is the builder's. Built-in platform jobs declare too. The stance lives on `JobDef`
  and in `describe`, **never in `FINGERPRINT`** (§3).
- **Signature.** `fn on_dead(self, tx: &mut Tx, dead: Dead<Self>) -> Result<(), JobError>`. A
  `scoped_by` job takes `ScopedTx` instead, and `cross_tenant` adds its capability, exactly as
  `run` does. Outbound jobs have the same hook.
- **`Dead<J>`** carries the attempt count and `last_error`, and for an outbound job its minted key,
  readable so the app can record it. It is neither `Clone` nor `Codec`.
- **Where it runs.** In the stage that commits the Dead mark, inside the job's tenant, through a
  `JobScope` and, for `cross_tenant`, a capability, both of which the dispatcher builds in every
  failure path as `run_due_into` does. The hook's effects (puts, deletes, enqueues, emits) and the
  Dead mark commit as **one record**. An outbound enqueue inside the hook (telling the patron, say)
  mints, as the job's group does. The public `Dispatcher::run_due`'s non-minting group refuses a
  hook's outbound enqueue by name, or mints. The builder picks one.
- **Which paths run it.** Every path to Dead through the failure record: a pure job's last App
  failure, and an outbound refusal, timeout, transport failure or settle failure. An unregistered
  name has no glue, so it goes Dead unhooked, as today, and GUIDE says so.
- **When the hook itself fails.**
  - An `App` error, a panic, or any of the three refusals the run path already counts as attempts
    is a hook failure. The hook-plus-mark stage is discarded, and a second stage commits the Dead
    mark alone with both errors recorded. The job arm's "at most two stages net one record"
    reasoning (dispatch.rs:422-435; mod.rs:893-901) becomes three, and its comments change with
    it.
  - A `JobError::Io` from the hook is not an attempt, as everywhere else: nothing commits, the
    error bubbles, the job re-dispatches after recovery, and the hook runs with the next failure
    record.
  - **The evidence a hook failure leaves** is durable, because it must survive Drive's kernel
    swap and restarts, which `KernelStats` does not. It must also be something app-supplied text
    can neither forge nor hide. With `JobRow` frozen, that is the combined `last_error` under a
    pinned, unambiguous format, or another durable trace the builder finds within §3.
  - `charpente_sim::checks` gains a check that reads that evidence and fails any universe in which
    a hook failed, and the scaffold includes it.

### D. A re-issue resends the same request under the same key

- **The API.** Only from inside `on_dead`: a re-issue (proposed `tx.reissue_at(when, dead)` and a
  relative form) consumes the `Dead<J>` and enqueues **the dead job's own payload, by name and
  bytes**, as a new Pending job carrying the dead job's minted key. It takes no new payload.
  - A key carries exactly one request. A different payload under it is the collision DECISIONS
    §14 exists to prevent: after a failover that loses the Dead record, timeline B re-dispatches
    the original while timeline A's re-issue calls with the same key. `Idempotent` answers such a
    request with a 409.
  - An app that wants a different request enqueues a new job, which gets a new key.
- **Provenance by type.** It never accepts an `IdempotencyKey` value. Because `Dead<J>` is
  consumed, there is one re-issue per Dead. A re-issued job that dies again gets its own `Dead<J>`
  with the same key, so a chain keeps one key and one request.
- **A pure job's re-issue** carries no key, since it never had one. It is a delayed re-enqueue of
  its payload.
- **The log.** The re-issue uses part B's record kind with a supplied key. The minting loop skips a
  supplied key and draws no `Entropy` for it.
- **The checker.** `keys_are_per_job` becomes per effect: every row that holds a key has the same
  name and the same payload bytes, and at most one of them is not Dead. Its failure text is
  re-pinned.
- **Docs.**
  - GUIDE §6's re-issue paragraph (GUIDE:2028-2033) is rewritten. A redrive from `on_dead`
    resends the same request under the same key. Any other re-issue is a new job with a new key,
    and its `call` must send an id of the effect.
  - DECISIONS §14 gains one sentence, a clarification and not a reversal: a re-issue copies a
    minted key together with its request, within the timeline that holds the Dead row, and never
    derives one.

### E. An outbound job reaches Dead in the sim

- **A provider-outage axis.**
  - It is sampled app-only, keyed, and on in a fraction of universes (§4 a).
  - It draws a host from the app's declared hosts once the app exists, a start inside the faulted
    phase, and a length in virtual time. The lengths span outages the default policy survives and
    outages that exhaust it.
  - During the window, every call to that host fails.
  - It is inert for an app with no hosts.
- **The outage outlives the quiesce.** `quiesce_outbound_faults` stops the per-call rolls, as
  today. A drawn outage still runs to its drawn end, because the tail is where a provider that
  stays down shows up as Dead. GUIDE §8's "fault-free tail" wording becomes "free of per-call
  faults; a drawn provider outage runs to its end".
- **Drive's tail runs until outbound work settles.** Once its horizon has passed, `recover`
  continues until every outbound job is Done, Dead or not yet due, bounded by a cap the builder
  sets and documents. Idle virtual time costs only a wake-up per retry, so a declared
  `retry(max = 12)` needs about a dozen steps, not 17 hours of work. No app has to size its
  horizon to its retry policy, and the sim never needs to read one. A tail that reaches the cap
  with outbound work still Pending fails by name.
- **`outbound_settles_by_horizon`** takes the time it judges at. A row not yet due at that time (a
  reminder days out, or a re-issue scheduled later) is not judged. Every other Pending outbound
  row still fails as "lost by the kernel". Its text is re-pinned.
- **Coverage.** A sim-side check scans the snapshot for Dead rows and marks a `dead:<job name>`
  coverage key, so an app's sim can `require:` that its Dead path ran. Under 0.4.0's rule, a
  required key that is never hit fails the batch. Drive's `recover` calls it, and a hand driver
  calls it itself.
- **Docs.** GUIDE §8's fault table gains the axis and the tail's new wording.

## 7. How we know it worked

1. **Text pins** for every new or changed line: the missing-stance compile error; the hook-failure
   record; the hook check's failure; the per-effect checker's failure;
   `outbound_settles_by_horizon`'s new text; the tail-cap failure; the no-time-source refusal.
2. **Determinism** as §4 states it, with each named step recorded before and after.
3. **Red before green.** Each of these fails first:
   - (a) an outbound job with the default retry policy reaches Dead under drawn swarm faults, not a
     scripted model, in a fixture (red today);
   - (b) a crash-point sweep over the Dead stage finds no state with the hook's effects but no Dead
     mark, or the mark but no effects, and a failing hook still leaves the mark;
   - (c) C's planted double fire: a re-issued outbound job sends the same key and the same request,
     and a remote that honours keys applies the effect once;
   - (d) a delayed job never runs earlier, in `sim.true_wall()`, than its due time minus the
     clock's offset at that moment as the sim models it. This is the sim's independent account
     of the node's clock, not the dispatcher's own assert. It also runs exactly once after a
     downtime;
   - (e) `tx.now()` is identical across two runs of a seed and never backwards within one process
     under the clock axes. Across a restart, it is behind the previous process's last reading by
     no more than §5 A's bound;
   - (f) a delayed outbound row not yet due passes `outbound_settles_by_horizon`, and a lost one
     still fails it.
4. **Replication and restart.**
   - The in-process replication suite shows a delayed job and a re-issue replicating, switching
     over and failing over with their due time, payload and key intact.
   - The edge harness's `clock_restart`, over clock-fixture's new delayed job, shows it running
     after a stock-binary restart, not before its time, and once.
   - Failover on stock binaries is not given a new vehicle. The new records ship as the same
     opaque frames, and apply is proven in-process. This is revisable if the plan finds a cheap
     vehicle.
5. **Mutation** over the changed code: every viable mutant is caught, or argued equivalent by name
   in `.cargo/mutants.toml`.
6. **The gate.** fmt, clippy with the deny-list, `cargo test --workspace --no-fail-fast` counted
   by `test result: ok`, the edge harness, and fresh-seed sim evidence at the repo's bar with N

   fall due within a run; an outbound effect whose provider can be out for longer than its retry
   budget; and something a user must be told when an effect is given up. The brief is committed
   before the run. It passes when:
   - (a) zero framework patches;
   - (b) no hand-built clock row and no cron sweep for due work;

   - (e) mutants run in its session are all caught or argued;
   - (f) review finds no Critical that a platform oracle should have caught.
