# 0.4.0 — the oracle as hard to get wrong as the app

**Date:** 2026-10-28, updated 2026-10-29 with a third agent's report. **Status:** written
from Noah's direction of 2026-10-28 ("you know exactly what the users of the product said"),
with no further questions to him. A builder check (2026-10-29) asked four questions and
found seven claims the code contradicted; every one was verified and settled from rules
this spec already states, so none went to Noah. Calls the controller made are marked as
such in §8.

## 1. Why

Three outside agents built on 0.3.0 and reported back (relayed by Noah, 2026-10-28 and
2026-10-29). Agent A built a commitment ledger (a five-state lifecycle, an outbound
notification job, a cron reaper, four sim properties, a mutation run). Agent B rebuilt its
0.2.0 newswire merge logic on drawn inputs and shrinking. Agent C built an agent runtime:
tenants, model calls and tool calls as outbound jobs, one settle per decision, a planted
double fire caught red with a shrunk seed. It reached green 256-run batches about 20
minutes after its first read. Noah's framing: agents are the main users of this product, so
what they hit outranks anyone's list of big items. Each claim below was checked against the
code, and two were reproduced with throwaway probes (deleted after reading).

What held. Deleting `tx.enqueue` or `tx.emit` in A's app went red. B's latest-wins mutant,
which survived 0.2.0's scripted inputs (0 of 119 runs failed), failed 230 of 994 runs on
drawn inputs, and two more bug classes from its real app were caught too. Every printed repro
command it ran replayed its failure. No guarantee broke.

What hurt was writing the checks, not the app:

1. **A second kernel on a spent App runs no jobs and no cron, and says the wrong thing.**
   `Kernel::build` moves the job definitions, outbound hosts and cron entries out of the App
   (`crates/charpente/src/kernel/mod.rs:314`, `:315`, `:333`). `Kernel::into_app`
   (`:1335`) hands back what is left. A second `Kernel::new` on it answers requests and
   nothing else. Probe, fault-free: cron ticked 10 times on the first kernel and 0 on the
   second, where a reopen ticked 10. A job enqueued on the spent App stayed Pending with
   `job "CountUp" is not registered — add it to the jobs![…] list passed to
   App::mount_jobs`, which sends the reader to a list that already has it. A's October
   regression test does exactly this: its `phase()` helper ends with `kernel.into_app()` and
   the next phase passes that App to `Kernel::new`. A read the result as "0.3.0 still owes a
   cron heap rebuild". **The statuspage build reported the same defect on 2026-09-21**
   (`docs/experiments/2026-09-statuspage/attempt-1/FINDINGS.md:97-110`; README item 4 at
   `:332`; `docs/LEDGER.md:5462`). It was ledgered as testimony and got neither a fix nor a
   PLAN row, so it came back. `examples/modelled_remote.rs`'s `run` helper still returns
   `kernel.into_app()`, the shape statuspage said invites it.

2. **A check that tested nothing passes the batch.** An untested check is labelled
   `untested`, never `ok`, but the batch exits 0, and the result line begins
   `sim result: ok` whenever another check passed (`docs/GUIDE.md:3238-3240`;
   `crates/charpente-sim/src/harness.rs:1403`). The 0.3.0 spec chose this as a controller
   call (its §4 "Exit codes") and lists it among calls Noah "has not yet seen in writing"
   (its §5 D). The same spec's §3 names as an anti-goal "a check reads green when it tested
   nothing". Both agents ranked vacuous green their hardest problem: A's reaper check on 0.1
   gave up 256 of 256 runs and read green; B's 0.2.0 amount property passed because scripted
   inputs never told latest from max. `require` and `floor:` exist and A used them, but they
   are opt-in, and the default is the one an agent meets first.

3. **Every app pastes the same recovery code, and the hand-written versions skip most runs.**
   B's `open_app` + `recover` (38 lines) and A's are nearly line for line the same. Both came
   from the shipped examples. All three examples carry their own copy
   (`restart_under_faults.rs`, `drawn_inputs.rs`, `modelled_remote.rs`), and so does the
   scaffold `charpente new` writes (`crates/charpente-cli/templates/sim.rs.tmpl`). A's first driver
   called `give_up` when the faulted phase's kernel died on fault fallout, so the crash the
   property is about counted as a skip, and nearly every run skipped. Skip rates seen: B's
   hand-fixed 0.2.0 driver 58% of runs, A's 0.3.0 ledger 27-37%, B's 0.3.0 rebuild with the
   copied example code under 1% (2-6 of about 1,000). Different apps and versions, so not a
   controlled comparison, but every hand-rolled driver skipped far more than the copied
   one. Of A's 75 productive minutes, writing and debugging the sim driver took about 40;
   the app took about 25. C's `tests/sim.rs` is 816 lines against 835 for its whole app,
   much of it a hand-written loop that re-sends unanswered requests after each reboot,
   rebuilt by hand because `Request` derives nothing and cannot be cloned
   (`crates/charpente/src/http/mod.rs:72`). Half of C's first batch and a quarter later
   skipped, because under write-error swarms no signup was ever answered. `drawn_inputs.rs`
   already re-sends unacked bids in its tail; re-sending is the fourth step every driver
   writes.

4. **The shrinker cannot delete an item that spans several draws.** Pass 1 deletes runs of 8,
   4, 2 or 1 choices (`harness.rs:444`). B's items are three draws each (template, acquirer,
   target), so one whole item never comes out in a step, and a partial deletion shifts the
   later draws so the run passes. Two of B's three shrunk failures kept an item they did not
   need. Probe with B's record shape (count 2 to 6, three picks per item, latest-wins against
   max): 38 of 105 failing seeds stopped above the true minimum `[0, 1]`, which fails; 24
   landed on `[1, 0, 0, 0, 1]`, B's own `--inputs 0100000001` choice for choice. With
   one-draw items, 178 of 178 reached the minimum. This is not PLAN's pair-search row
   (0.3.0 ruling R39), which is about equal choices that must move together.

5. **A mutation run does not fit in a working session.** A's scoped run: 8 mutants, one
   property, `--jobs 2`, 28 minutes, about 440 s of sim per mutant at the default 256 runs.
   Mutation was the largest single block of A's productive time. The verb has no way to judge
   a mutant at fewer runs (flags: `--file`, `--re`, `--timeout`, `--jobs`, `--test-package`,
   `--property`), and each mutant's batch draws its own ambient master seed
   (`harness.rs:921`, `lib.rs:2573`), so two runs of the verb judge different universes.

6. **The mutants verb blames the wrong cause for a common baseline failure.** cargo-mutants
   27.1.0 copies the tree to a scratch directory and rewrites relative paths only in
   `[dependencies]`, `[replace]` and `[patch]` (`fix_manifest_toml`, `src/manifest.rs` at
   the v27.1.0 tag); `[dev-dependencies]` stay relative. Every charpente app has
   `charpente-sim` as a dev-dependency, so an app that takes charpente by relative path
   fails its unmutated baseline. The verb's error (`crates/charpente-cli/src/mutants.rs:580-583`)
   names tests that shell out via `CARGO_BIN_EXE_…` instead. A also lost a run to a 512 MB
   tmpfs `/tmp` filling during the scratch build, and nothing named `TMPDIR`. crates.io users
   and the experiments' `[patch.crates-io]` briefs are not affected; the setups Noah uses to
   test unreleased versions are.

7. **The failure block carries noise and one misleading label.**
   - It prints the whole 27-field `FaultConfig` Debug dump (`harness.rs:1790`), mostly
     zeros, above a `fired:` line that already says what fired. B and the pricewatch build
     both said so; pricewatch: "I could not have got this from the `config:` line".
   - The `first:` line (`harness.rs:1824`) prints whenever the shrunk run's message text
     differs from the first failure's. Messages carry values, so it prints after almost every
     shrink. B took it for a different failure; in all of B's cases it was the same assertion
     with different values.
   - GUIDE §8 says both that `run` returns "once nothing is left inside the horizon"
     (`docs/GUIDE.md:3771`) and that it returns "when its source is exhausted" (`:3985`). The
     second invites the belief that an empty source ends at once. A's October test pushes a
     dummy request for that reason; the first probe above ran an empty source to its full
     horizon with cron ticking.

8. **How the agents read.** A read GUIDE closely. B opened no GUIDE section body at all: it
   learned 0.3.0 from `examples/drawn_inputs.rs` alone, and 0.2.0 from framework source and
   tests. C read GUIDE in 400-line chunks (about 1,200 of §8's 2,150 lines), took
   `examples/invoicing` as its real spec, and still grepped `charpente-core` for
   signatures: `EventRow`'s fields, `scan_scoped`, `scan_from` (which does not resolve
   until `View` is imported). It asked for one page listing every attribute, transaction
   method and sim helper with its signature. GUIDE prose reaches one reading style; example
   code and error text reach all three, and the type system reaches every agent. GUIDE does
   say the remote's side is not exactly-once (`docs/GUIDE.md:2162-2167`), and B asked for
   that sentence anyway.

9. **A re-issued effect gets a fresh key.** The minted key is per job: it survives every
   retry and re-dispatch, and `enqueue_keyed`'s app key is never sent
   (`docs/GUIDE.md:1997-2006`). GUIDE's outbound example sends `key.as_str()` (`:1938`,
   and again at `:4227`). An app that enqueues the same effect twice (a redrive after a Dead
   job, a re-issued step) sends two keys, and a remote that honours keys applies both. GUIDE
   says nothing about re-issue. C planted exactly this double fire, and the sim caught it.

10. **Events are read by hand.** The checker library has no typed event read
    (`crates/charpente-sim/src/checks.rs`). A wrote a 40-line `event_counts` with one decode
    arm per event; C grepped core for `EventRow`'s fields and the scan signatures.

11. **A private handler in a submodule cannot be mounted, and the error is about code the
    agent never wrote.** `#[route]` gives its generated struct the handler's own visibility
    (`crates/charpente-macros/src/route.rs:511`, and `:852` in the second macro), so
    `routes![m::handler]` fails with E0603 on a struct the macro made. Nothing says "make the
    handler `pub`".

12. **What the app builds because the platform does not.** A Dead job is invisible to an
    app: no hook fires, and apps cannot read `JobRow`, so C built a watchdog and a redrive,
    about a third of its jobs code. That meets the trigger of PLAN's row "Dead reachable in
    the sim, and a hook or documented path for an outbound job that goes Dead": the first
    app that must act on an outbound effect it gave up on. A and C each built a logical
    clock (an `AppClock` row advanced by cron), because a transaction has no time. No PLAN
    row covers that. It shares 0.3.0 ruling R3's cost: a time the log can replay is a new
    log record, which changes the log format and every pinned seed's byte counts.

C's four root-only test failures are the suite working: `chmod_that_bites`
(`crates/charpente/tests/support/mod.rs:14-40`) fails such a pin on purpose with "this pin
needs a non-root runner". No change.

Asked to rank, A put first a spec language that generates the app, then templates for
common properties with vacuity as failure, then helpers for the recovery code, then
structured errors and a fix verb, then session-sized mutation, then a state-machine
language. B ranked vacuous properties, then unreadable skips, then non-minimal shrinks.
C asked for a hook when a job goes Dead, a caller-chosen key on enqueue, a deterministic
`tx.now()`, a supervise helper with typed event reads, a one-page API sheet, and gentler
faults at startup.

What recurs across all three agents and the six earlier builds is item 3, then item 2, then
the reading problem in items 8 and 10. Those, plus the defects above, are this release.
Item 12 recurs too, but it is the app's side of the platform, not the oracle's, and part of
it needs a log format change. §2 schedules it as the next release.

## 2. Goals, non-goals, anti-goals

**Goals.**
- A blind agent writes a sim test for its app without pasting recovery code, and the only
  thing it supplies is how to build its app.
- A check that tested nothing fails the batch, and the output says where its runs stopped
  and what to change.
- A shrunk failure carries no item the shrinker could have deleted, for items of up to
  eight draws.
- `charpente test --mutants` answers a scoped run inside a working session, with the same
  verdicts a full-strength run would give.
- Misuse an agent has made twice stops being expressible: no second kernel on a spent App.
- A sim test reads the app's events as the app's own types.
- An agent finds the signature of anything an app or a sim test names on one page, and that
  page cannot drift from the code.
- Every finding a docs-only or stranger build reports ends with a disposition.

**Non-goals**, each with where it goes:
- **A spec language that generates the app** (A's first ask). Generation is autocomplete,
  and MANIFESTO §3 says the winner is the best reviewer, not the best autocomplete. Its
  concrete pain (lines the agent reproduces by hand) is addressed where it is an oracle
  problem, by part C, and where it is a type problem, by the rows below. Refused, not
  deferred.
- **A state-machine declaration** (A's sixth ask). Every app so far hand-writes one
  (invoicing, helpdesk, statuspage, the ledger), so it is a PLAN v1.x row. Trigger: a
  docs-only build's mutation run misses a mutant in a state transition's match, or its
  review finds a Critical a declared transition table would have refused.
- **Properties the framework derives from an app's shape** (A's second ask, the template
  half), such as an event-proof check for every route that emits. It is the strongest answer
  to "who writes the oracle", and too large for this release. PLAN v1.x row. Trigger: a
  docs-only build's mutation run misses the deletion of a `tx.enqueue` or `tx.emit`.
- **A derive for an enum's `Codec`.** GUIDE §2 teaches a hand-written tag table
  (`docs/GUIDE.md:224-230`), where a misnumbered tag compiles. A derive numbering by
  declaration order makes reordering variants a silent format change, which is the deep
  fingerprint row's problem. PLAN v1.x row beside that one. Trigger: the first misnumbered
  tag found in a docs-only build or a review.
- **Structured compiler errors and a fix verb** (A's fourth ask). cargo already emits JSON
  diagnostics (`--message-format=json`), the sim has `--format json`, and machine-applicable
  suggestions from a proc macro need unstable `proc_macro::Diagnostic`. Nothing to build.
- **What the app builds because the platform does not** (§1 item 12): a hook committed with
  a job's Dead mark, a re-issue that keeps the effect's key, and a transaction's own time.
  C meets the Dead row's trigger, so that row is due; A and C both built a clock by hand,
  which is new evidence with no row yet. They are the next release, 0.5.0, not this one:
  they are the app's side of the platform, the time work moves the log format and every
  pinned seed, and 0.4.0's docs-only build should measure the oracle changes alone. PLAN
  records them with this testimony. 0.4.0 carries only the warning in A.6.
- **Gentler faults at startup** (C), and any change to fault rates or the skip rate. "The
  give-ups are the fault rate" (2026-09-07) stands. The skips C describes are setups that
  never got an answer, and part C's tail re-sends what went unanswered, which is how B's
  copied driver skipped under 1%. Part C removes skips the driver causes; it does not touch
  skips faults cause.
- **A host that is not a literal** in `#[job(outbound = …)]` (C). The literal is what puts
  every host into `describe` (0.3.0 spec §3); PLAN's "one outbound job over several declared
  hosts" row stands.
- **A stranger re-run** of the launch rehearsal. The output changes here are small and the
  docs-only build in §6 reads them. Controller call (§8).

**Anti-goals.** It fails even if it works when:
- a platform pinned seed or recorded batch decides differently and this spec does not name
  why;
- a check that tested nothing exits 0 anywhere but a single-seed replay;
- the quick mutation pass reports a verdict a single full-strength pass would not;
- the helper hides a give-up: a crash in the faulted phase becomes a skip, or a tail that
  cannot boot without a durable refusal becomes anything but a failure;
- the shrinker reports an input that does not fail when its own printed command replays it.

## 3. Constraints

- **Hard rules 1-6** as written in CLAUDE.md. In particular: every new output line and
  refusal is pinned by a test against its exact text (5); GUIDE, CHANGELOG and examples
  change in the commit that changes the behaviour (6); each defect gets its failing test
  before its fix (3).
- **Determinism.** Four changes move recorded output on purpose. Each is a named step, lands
  once, and records its before and after:
  - A.1 moves merge-fixture's pins (its driver re-kernels a spent App today);
  - B moves any recorded batch that held an untested check, and any platform suite in which
    every universe gave up;
  - C moves the examples' and the scaffold's recorded output, because the helper picks one
    behaviour where their drivers differ (C lists the differences);
  - D moves shrunk inputs and replay counts.

  Nothing else moves: every other pinned seed and recorded batch decides exactly as before.
  Two runs of one batch, and runs at `--jobs 1` and `--jobs N`, still print byte-identical
  output.
- **Dependency edges.** `charpente-sim` depends on `charpente-core` alone today, and
  `Kernel` and `App` live in `charpente`. No new edge inside the deterministic boundary
  without a stated reason in the plan.
- **Numbers.** docs/BENCH.md is the only source of quotable performance numbers. GUIDE says
  what the quick mutation pass does, not how much faster it is, unless a measurement lands
  in BENCH first.
- **No compatibility** (Noah, 2026-10-22). Breaks land in place and CHANGELOG lists them.
- **Exit codes:** 0 green, 1 any failure, unmet `require` or untested check, 2 usage, build
  or infrastructure. A `--seed` replay of a skipped run still exits 0.
  *Amended in execution (2026-10-31): a quick pass (`CHARPENTE_SIM_FIRST_RUNS`, §4 E) is the
  second exception, judging failed runs only; `require` and the untested rule are judged at the
  full count, as §4 E says.*
- **Version:** 0.4.0 for all six crates. 0.3.0 is on crates.io (the registry's
  `max_version`, checked 2026-10-28; the repo has not recorded the publish yet, since
  CHANGELOG still says "unreleased" and the ledger has no close-out, both Noah's), and removing `into_app` is a
  breaking change, which Cargo's rules for 0.x put in a minor bump. `charpente new` writes
  `"0.4"`.

## 4. The parts

### A. The small fixes

1. **No second kernel on a spent App.** The misuse must not compile. Recommended shape:
   remove `Kernel::into_app`; reading the end state goes through `kernel.app()` and
   `kernel.app_mut_for_tests()`, which exist. A helper that hands back an end state returns
   the `Kernel`. The 37 call sites (29 in `charpente`'s own tests, the invoicing,
   merge-fixture and outbound-fixture sims, `modelled_remote.rs`, two GUIDE code blocks at
   :3967 and :4350, and GUIDE's prose at :3775, which teaches `into_app` as the way to read
   end state and is rewritten) move to that. One of them is the defect itself:
   merge-fixture's driver builds a new kernel on the spent App for every bid
   (`crates/merge-fixture/tests/sim.rs:67-77`). It works only because that app has no jobs,
   and the built-in session-sweep cron silently stops after the first bid. It moves to one
   kernel per process lifetime, rebuilt only after a stop, as a supervisor would. That
   moves its pins (`shrunk: 11 draws to 5` at :196, and master seed `0xe27fde2a57487fee`,
   chosen at :198-216 because its first failure is on lab 2), a named step (§3). The
   oracle's meaning must survive the move: the latest-wins mutant survives the scripted
   workload, dies under drawn inputs, and shrinks to two arrivals, the later one smaller.
   Whatever refuses the misuse, the doc comment a reader lands on names the two sanctioned
   shapes: run the same kernel again against another `SimSource`, or restart the process
   and rebuild the app. Before the fix, a test reproducing the probe goes red; after, a
   trybuild case pins the refusal.
2. **The mutants verb refuses a dev-dependency path cargo-mutants will not rewrite.** Before
   the timing run, read the manifest of every package the run tests. A relative `path` under
   `[dev-dependencies]`, `[build-dependencies]` or any `[target.*.…-dependencies]` table that
   points outside the tree cargo-mutants copies is refused, exit 2, naming the manifest, the
   table, the dependency, why (cargo-mutants 27.1.0 rewrites only `[dependencies]`,
   `[replace]` and `[patch]`), and the fix (an absolute path, or `[patch.crates-io]`). A
   baseline that fails for lack of disk space names the scratch location and `TMPDIR`.
3. **The failure block.**
   - The human block drops the `config:` line. JSON keeps the config.
   - `first:` becomes a label that says what it is, such as `before shrinking:`.
   - GUIDE:3985 says `run` returns once nothing is left inside the horizon, as :3771 does.
   - Every GUIDE block, example comment and pinned text that shows the old lines moves with
     them.
4. **The remote's side, where B would have read it.** The sentence GUIDE carries at
   :2162-2167 (the app's state stays exactly-once, a remote that ignores the key may apply a
   retry twice) also goes into `examples/modelled_remote.rs`, next to the gateway model.
5. **A handler mounts from another module.** A `routes![…]` or `jobs![…]` that names a
   handler or job in another module of the same crate compiles whatever the handler's own
   visibility, or the error names the fix in words. Today it is E0603 on a macro-generated
   struct.
6. **A re-issued effect and its key.** GUIDE §6's "Outbound jobs" and `modelled_remote.rs`
   say plainly: the minted key belongs to one job and covers its retries; an effect the app
   may enqueue more than once (a redrive, a re-issued step) must carry an id of the effect
   itself in the call, or a remote that honours keys applies it twice. Platform support for
   re-issue is 0.5.0 (§2).

### B. A check that tested nothing fails

- In a batch, any check with zero tested runs makes the batch exit 1. That includes a batch
  narrowed by `--filter`, and the case where every check is untested. A `--seed` replay of a
  skipped run is unchanged: it prints the run's reason and detail and exits 0.
- The check line keeps `untested  (0 tested, N skipped)`. The result line does not begin
  `sim result: ok`. A line after the skipped-reasons block names the fix: the reasons above
  say where the check's runs stopped, so change the setup until runs reach the check
  (pointing at part C's helper), or delete the check.
- JSON: the check's `status` stays `untested`, and the batch result and exit code follow the
  human output.
- Under `charpente test --mutants`: a baseline with an untested check is a baseline that is
  not green (exit 2), and the error names the untested check rather than any other cause. A
  mutant that leaves a check untested makes the sim exit 1, which cargo-mutants records as
  caught. That is right: the suite noticed the change, and anyone reading that run's output
  sees `untested` and why.
- The platform's own runners, `run_universes!` and `run_universes_swarm!`, follow the same
  rule: a test in which every universe gave up fails. Today they print "every universe gave
  up" and pass (`crates/charpente-sim/src/lib.rs:2497-2509`). Seed derivation does not
  change, so the runners stay frozen in the sense the 0.3.0 plan meant. A platform suite
  that newly fails is a vacuous platform test, and it is fixed in this release.
- This reverses the 0.3.0 controller call. GUIDE §8 ("Reading a batch" and the untested
  passage at :3238), the 0.3.0 spec's exit-code line and DESIGN §7 if it states the codes
  change with it.

### C. The recovery helper

Every example and all three agents wrote variants of the same steps. Where the shipped
drivers differ, the differences decide runs:
- On a first boot that fails on fault fallout, `restart_under_faults.rs:102-107`,
  `drawn_inputs.rs:140-145` and the scaffold (`sim.rs.tmpl:80-84`) give up, while
  `modelled_remote.rs:190` skips the faulted phase and goes on to the tail.
- The first boot's fallout test is `is_fault_fallout` alone in the first three, and also
  `clock_fallout` in `modelled_remote.rs:151-157`.
- Two tails only boot. `drawn_inputs` runs a re-send source; `modelled_remote` runs to a
  600 s horizon and reports a kernel stop in its own words.
- Only `drawn_inputs.rs:170-196` re-sends. It re-sends every non-200 and merges the
  answers back into the faulted phase's (`:194-196`).

The steps become library functions with one behaviour each, and the app supplies only how
to build itself and what to send. Adopting them moves the examples' and the scaffold's
recorded output once, a named step (§3).

1. **Boot through fallout.** What `boot_through_fallout` does today. A first boot that never
   gets past fault fallout is not a give-up: the faulted phase is empty, and the run goes
   on to the tail, where step 4 sends everything. That is `modelled_remote`'s choice, and
   it turns a skipped run into a tested one. Fault fallout means `is_fault_fallout` or
   `clock_fallout`, in every step.
2. **A faulted phase.** Run a kernel over a source under faults. Fault fallout ends the phase
   and is the crash under test: never a give-up, never a skip. A non-fallout error is a
   failure. The replies already recorded stand.
3. **A fault-free tail.** Quiesce every fault family the run uses (disk, clock, and outbound
   when the app declares hosts), wait out a clock refusal, boot, build the kernel (with the
   outbound handle when the app declares hosts), and give up only on a durable refusal. A
   tail that cannot boot otherwise is a failure, as the examples' `"the fault-free tail could
   not boot"` is today. The tail then runs the kernel to a horizon the caller gives, so
   due jobs, retries and cron drain; a kernel stop there is a failure, reported in the
   kernel's words. A remote model's own switches (`modelled_remote`'s `calm`) stay in the
   app's code.
4. **Re-send what went unanswered.** In the tail, every request the faulted phase left
   without an answer is sent again: no reply recorded, or a reply whose body is fault
   fallout. A 4xx is the app's own answer and is not re-sent. This is what C's `supervise`
   loop did after every reboot and what `drawn_inputs.rs` does by hand. A re-sent request's
   answer is reported apart from the faulted phase's, because an unanswered request may or
   may not have landed, and the app's claims must not treat the two the same. A check that
   wants them merged, as `drawn_inputs` does, merges them itself. `Request` becomes `Clone`,
   or the helper takes the requests in a form it can send twice. Re-sending is the path the
   examples and the scaffold teach.

Alongside the steps, **typed event reads**: the checker library reads the durable event log
as the app's own event types, global and per tenant, so no sim test decodes `EventRow` by
hand or grepping core for its fields.

Requirements:
- The decision "a crash in the faulted phase is not a skip" lives in the helper and nowhere
  else.
- The three shipped examples and the scaffold template (`templates/sim.rs.tmpl`) switch to

### D. The shrinker deletes whole items

A shrunk failure carries no item the shrinker could have deleted, for items of up to eight
draws. The oracle is the probe from §1 item 4, kept as a harness test: a check that draws a
count from 2 to 6 and then three picks per item, failing on latest-wins against max. Every
seed in a fixed range whose first failure fails must shrink to the minimum, two items,
within the budget. Its one-draw twin stays as the control. Two mechanisms are candidates:
- trying every chunk length from 1 to 8 in pass 1, not only 8, 4, 2 and 1;
- deleting the span between repeats of a draw name, which the harness already records for
  the `inputs:` line.

The R39 history in the shrink doc comment (`harness.rs:296-341`) is the warning: passes that
spend the budget early leave fault axes on and fault-coupled inputs high, which misdirects
the fix. Every existing shrink test stays green. GUIDE §8 "Shrinking a failure" describes
the new pass.

### E. A mutation run that fits a session

- The verb pins one master seed for the whole run and prints it with a rerun command, so
  every mutant is judged on the same universes and a run can be repeated.
- Each mutant is judged first on the first N runs of each check. In that pass only a failed
  run counts: a run whose check returned an error is a catch, because a red run proves
  itself. Coverage requirements (`require`, `floor:`, `ceiling:`) and the untested rule
  depend on how many runs there are, so they are judged only at the full count. One that
  is missed or times out in the first pass is judged again at the full count. The final
  verdicts equal a single full-strength pass exactly.
  *Amended in execution: a mutant that fails an early run and then hangs is caught in pass 1 where a single full pass would time out; every other verdict is equal.*
- The first pass derives every check's seeds for the full count from the pinned master seed
  and runs only the first N of each. Seeds today come from one stream across checks
  (`harness.rs:1105-1111`), so running the batch at `--runs N` would give every check after
  the first different universes. Deriving for the full count keeps the first pass's runs a
  prefix of the second's for every check, and moves no recorded batch.
- The unmutated baseline is judged the same way: the first-pass baseline counts failed runs
  only, and part B's rule and the coverage requirements apply to the full-count baseline.
- The timeout for each pass is set from a baseline timed at that pass's run count, as the
  verb sets one today.
- The report says which pass decided each mutant, and the totals.
- The full count is the sim's default unless the run says otherwise.
- The quick pass applies to app batches (`sim_tests!`), which is where the verb's users
  are. The platform's own `run_universes!` suites write their run counts in source and
  measure their floors and ceilings at a pinned base (`lib.rs:2808-2818`), so the verb
  judges them in one full pass, and its report says which test packages it judged that way.

### F. The API on one page

One page lists everything an app or a sim test names: the attributes and their arguments,
`Tx` and `ScopedTx` methods, the `App` builder, `Kernel` and `SimSource`, `Sim`'s methods
and inputs, and the checker library. Each entry shows its use with types, in as little text
as fits. The page is Rust that `crates/guide-examples` compiles, the way it compiles
GUIDE's blocks today, so a signature that changes breaks the build rather than the page. It
ships inside the crate where GUIDE does, and GUIDE's opening, before §1, points to it
first. It is a
reference, not a tutorial (DECISIONS §3 puts error text ahead of tutorials, and this changes
nothing there). A census test holds that every public item in the listed surfaces appears on
the page, so a new method cannot ship without its line.

## 6. How we know it worked

1. **Text pins** (hard rule 5) for every new or changed line: the untested result and its
   fix line, the dev-dependency refusal, the disk-space naming, the renamed label, the
   mutants report with its passes, seed and rerun command.
2. **Determinism** as §3 states it, with the four named steps recorded before and after.
3. **Red before green** for each defect: the spent-App probe; a batch with an untested check
   exiting 0; the record-shaped shrink stopping above its minimum; a relative dev-dependency
   failing the baseline with the wrong message.
4. **The quick pass is exact.** A fixture with at least one mutant that only a run past the
   first pass's count catches (the control that shows the second pass matters) and one that
   the first pass catches, and one whose only red at the first pass's count would be an unmet
   `require` (the control that shows the first pass counts failed runs only). The verb's
   classification equals a single full-strength run's, mutant by mutant.
5. **The helper census** in guide-examples, red with a copied `recover` left in an example,
   green after. **The API page's census**, red with a public method left off the page,
   green after; and the page itself compiling.
6. **Mutation** over the changed code in charpente, charpente-sim and charpente-cli: every
   viable mutant caught, or argued equivalent by name in `.cargo/mutants.toml`.
7. **The gate.** fmt, clippy with the deny-list, `cargo test --workspace --no-fail-fast`
   counted by `test result: ok`, the edge harness, and fresh-seed sim evidence at the repo's
   bar with N stated. CI and the nightly are Noah's.
8. **A docs-only build** (M3 sub-project 3's bar). A fresh agent, offline, given only what
   ships in the 0.4.0 crates, builds an app in a new domain whose correctness rests on a
   lifecycle with at least four states, an outbound effect, and inputs drawn as items of
   several draws. The brief is committed before the run and gives the domain only. It
   passes when:
   - (a) zero framework patches;
   - (b) its sim tests use the helper and the typed event reads, and contain no
     hand-written recovery, re-send loop or `EventRow` decode;
   - (c) its final batch has no untested check;
   - (d) it runs `charpente test --mutants` inside its session, and every viable mutant is
     caught or argued equivalent by name;
   - (e) any shrunk failure it reports has no item the controller can delete with the
     failure still replaying;
   - (f) review finds no Critical a platform oracle should have caught.

   Every finding it reports gets a disposition under G's rule before the publish. A miss is
   a finding: fix it and run a new attempt, recording both.
9. **After the publish** (Noah's hand): install, `--version`, `new`, clippy, sim.
