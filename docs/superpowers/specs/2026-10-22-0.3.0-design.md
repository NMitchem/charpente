# 0.3.0 — time that survives a restart, inputs the sim draws, output an agent can act on

**Date:** 2026-10-22. **Status:** approved by Noah, 2026-10-22. The builder check's answers
are folded in as they arrive; any that change what gets built go back to him. **Supersedes**
`2026-10-17-readable-sim-output-design.md` (0.2.1) and its plan. This release absorbs both,
and they are removed in the commit that adds this file. Their history stays in git
(`d972ef9d`, `342cfb58`).

## 1. Why

Two outside agents built apps on 0.2.0 and reported back (relayed by Noah, 2026-10-22).
Each claim below was checked against the code.

1. **Production time is process uptime.** `ProdClock` (`crates/charpente/src/prod.rs:18`)
   counts nanoseconds from its own construction, and `serve` builds a fresh one for every
   process (`serve.rs:127-128`, and again at `:178`, `:238` and `:296`). Every time the
   platform stores or compares is on that scale:
   - **Cron.** `CronScheduler::upsert` keeps a row's `next_due` (`kernel/cron.rs:56`). After
     a restart, a schedule stays silent until the new process's uptime passes the old one's.
     GUIDE §7 (`docs/GUIDE.md:2591`) says a schedule's phase survives restarts. The first
     agent's regression test: 72 ticks before a restart, 0 after.
   - **Sessions.** `expires_at = now + session_ttl` (`http/app.rs:224`). After a restart or
     failover, a session outlives its TTL by the old process's uptime. DESIGN §8
     (`DESIGN.md:2123-2125`) says expiry holds "restart or not".
   - **OIDC.** `exp`/`nbf` are Unix seconds, compared against uptime nanoseconds
     (`auth/oidc.rs:320-329`). In production an expired token is never refused, and any token
     carrying `nbf` is always refused. The tests pass because they hand `verify` a Unix-scale
     `now` (`crates/charpente/tests/http.rs:739`).
   - **Jobs and keys.** `JobRow.due_at` (`charpente-core/src/job.rs:80`, set by `enqueue_in`
     and by retry backoff) and `ApiKey.created_at` (`http/app.rs:242`) are on the same scale.

   DESIGN already requires the opposite. It names a "restart-stable `Clock`" (`DESIGN.md:2125`)
   and converts JWT seconds "to the clock's nanos" (`:2115`), so this is production breaking a
   written contract, not an open design question. The sim missed it because its clock is one
   continuous world clock. Nothing models the clock a restarted process sees, and
   `FaultConfig` has no clock axis, though MANIFESTO §6 lists clock skew among the faults the
   simulator injects. Status of the evidence: traced in source, and the cron half reproduced by
   the first agent's test; no test in this repo reproduces it yet (part B's first step does,
   per hard rule 3).

2. **The sim draws the world's faults but not the app's inputs.** The second agent's app (4
   feeds, 7 stories, 3 noise items, an LLM stand-in) scripted every input by hand. A "latest
   wins instead of max amount" mutation survived all 119 universes, because the scripted
   arrival order made the latest event the largest in nearly every universe. Both of its real
   bugs were caught only on titles he happened to script. He shrank a failing 7-story universe
   to "two acquisitions by the same lab" by hand. `charpente_sim::rng::Rng` is public, and
   GUIDE §8 uses it to model remotes, but nothing teaches drawing a workload's inputs, the
   scaffold scripts one POST, and nothing shrinks. MANIFESTO §9's wager, "every path through
   this system has been executed, under fault, thousands of times", depends on inputs: under
   scripted inputs, thousands of universes walk one business path under different faults.

3. **The scaffold proves two of its three effects.** `crates/charpente-cli/templates/lib.rs:59-60`
   enqueues `Echo` and emits `NoteAdded` in one transaction. Neither sim property checks the
   event, so deleting `tx.emit` stays green. This is the same class as item 2: a property that
   cannot fail, because nothing makes the distinguishing case happen.

4. **Agents learn from what ships, and GUIDE does not ship.** None of the six 0.2.0 crates
   contains GUIDE.md. The registry copies hold `src/`, `tests/` and, for two of them, the
   README. The second agent found "no doc on wiring fake remotes" (GUIDE §8 has one) and read
   the platform's own tests instead. In his words: "whatever the error message says is what I
   do next", and "your tests are your documentation whether you meant it or not."

5. **The 0.2.1 items, never shipped.** The sim summary cannot be read cold (launch-run
   testimony; Noah, 2026-10-17: "I have no idea what 334 of 512 means"). `charpente --version`
   prints the usage text. README's clippy line assumes the clippy component is installed.
   README's "the second property goes red" does not name the property. The second agent added
   three nits: `charpente_sim` does not re-export `OutboundCall`/`OutboundReply`, CHANGELOG
   still says "0.2.0 (unreleased)", and the scaffold needs `rustup component add clippy
   rustfmt` without saying so.

Every item meets PLAN's test for after-launch work: does it make the reviewer catch more, or a
stranger's first hour shorter? Item 1 is a correctness and security defect in both published
releases. Nobody uses the platform yet (Noah), so the fix ships in this release rather than in
a patch.

## 2. Principles this release writes down (Noah, 2026-10-22)

"Nothing needs to be backwards compatible. The goal for charpente is the manifesto, not
backwards compatibility." When applicable:

- **APIs change in place.** A changed API is changed, not given a parallel. The break arrives
  as a compile error that names the fix, which costs an agent seconds. The minor version
  bumps.
- **No migration for old data.** A data directory or a replication peer from an older
  charpente minor is refused by name, with the fix in the text (hard rule 5). It is never
  converted.

Scope (the controller's reading of "when applicable"): these cover charpente's own APIs,
output, JSON, and on-disk and wire formats, across charpente releases. An app's own data
across the app's own deploys stays guaranteed: `migrate_schema`, payload shapes, the upgrade
barrier. DESIGN §3 and DECISIONS §5 ("log-replay upgrades") rest on that guarantee, and it is
the user's data, not charpente's.

Where they land: one line in MANIFESTO §8 (what we refuse to build: a compatibility layer), a
new DECISIONS §15 entry with the reasoning and a reopen condition, and the rule in DESIGN.
They land first, before any code, because every part below applies them.

## 3. Goals, non-goals, anti-goals

**Goals.**
- Every time charpente stores or compares means the same thing after a restart, a failover or
  a wall-clock step, and the sim injects the clock behaviour that would break it.
- A workload can draw its inputs from the run. A failure shrinks to the smallest inputs and
  faults that still fail. The scaffold and GUIDE teach both.
- A person or an agent reads `charpente test --sim` cold and can say, for each check: did it
  hold, how many runs tested it, how many distinct inputs those runs covered, why the rest
  were skipped, and how to rerun it.
- What an offline agent finds inside the crates is what we mean it to copy.

**Non-goals**, each with where it goes:
- **Coverage-guided fault or input search** (the second agent ranked it first). Its concrete
  case is caught by plain seeded inputs: with arrivals in a random order, the latest is also
  the largest in about one run in n. Steering a run by what earlier runs covered would break
  "one seed names one run". It becomes a PLAN v1.x row. Trigger: a mutant that survives
  generated inputs because the case that distinguishes it is too rare for uniform draws.
- **An input DSL.** Generators are Rust, so the types stay the oracle (MANIFESTO §6).
- **MCP or any agent-integration contract**, and **one job over several declared hosts** (the
  second agent's convenience items: four near-identical job structs, because `outbound` takes
  a literal host). The literal is what puts every host an app calls into `describe`. Both
  become PLAN v1.x rows. Triggers: the first app whose consumer is an agent calling it as
  tools; the first app where duplicated outbound jobs cause a defect.
- **Measuring a real model.** The second agent saw poor live recall on terse HN titles. A
  generator tests how the app handles what its model stand-in returns, never the real model.
  GUIDE §8 says so.
- **Changing fault rates or the skip rate** ("the give-ups are the fault rate", settled
  2026-09-07), the platform's internal suites' runner line, and `charpente test --mutants`
  output.
- **Old 0.2 data directories, peers or apps** (§2).

**Anti-goals.** It fails even if it works when:
- a platform pinned seed decides differently and this spec does not name why (§4);
- a check reads green when it tested nothing, or the output softens a failure;
- the shrinker reports an input that does not fail when its own printed command replays it;
- the reasons or inputs shown are noise: hundreds of one-off lines, or text that differs
  between two runs of the same batch, or between `--jobs` values;
- the clock fix is proven only in the sim. The sim's continuous clock is why the bug hid.

## 4. Constraints

- **Hard rule 1.** `SystemTime` enters only `prod`, the one deny-list-allowed IO module.
  Nothing in the harness's accounting reads a clock: the shrinker's budget is counted in
  replays, never in time.
- **Determinism.** New random behaviour draws from its own keyed stream (the
  `object_delete_error` precedent, PLAN M2). So a workload that draws no inputs, run with the
  new fault axes off, decides exactly as before: same failures (check, seed, message), same
  tested and skipped counts, same coverage. Adding the clock axes moves none of the swarm
  config's existing draws. Where a change has to move a recorded batch, it moves once, in a
  named step, with the before and after recorded. The known steps are the app harness turning
  clock faults on, the sim's starting instant (B), and the fixtures and scaffold moving to
  drawn inputs (C).
- **Exit codes:** 0 green (a batch where every check is untested included), 1 any failure or
  unmet `require`, 2 usage, build or infrastructure.
- **Hard rule 3:** each clock defect gets its failing test before its fix.
- **Hard rule 5:** every new output line and every new refusal is pinned by a test against its
  exact text.
- **Hard rule 6:** docs land with the code. GUIDE sections touched: §1 (scaffold), §5 (session
  and OIDC expiry), §6 (job due times), §7 (cron), §8 (inputs, shrinking, the output, the
  clock faults, the model boundary), and §13 if `describe` changes. Also CHANGELOG (0.3.0) and
  README's "Try it".
- **Version:** 0.3.0 for all six crates. `charpente new` writes `"0.3"` (the major.minor
  convention, unchanged).

## 5. The parts

### A. The principles (§2)

These land first.

### B. Restart-stable time

DESIGN decides the direction (§1 item 1), so it is not reopened: production `now` is
wall-clock time, nanoseconds since the Unix epoch, the scale the JWT conversion already
assumes.

- **One clock per node.** `serve`'s separate kernel and source clocks (`serve.rs:127-128`)
  become one.
- **`now` never goes backwards** across a wall-clock step, a restart or a failover. When the
  wall clock steps back, `now` holds until the wall clock passes it again. TigerBeetle's clock
  is the prior art to read first. The mechanism is the builder's (for example, a high-water
  mark recovered from the log), but it must hold across a restart, not only within one
  process.
- **A pre-0.3 data directory is refused at open, by name.** Its stored times are on a scale
  0.3 cannot read (§2). `PROTO_VERSION` bumps, so the existing named refusal turns away a 0.2
  peer.
- **The sim runs at production's scale.** Its world clock starts at a Unix-scale instant.
  New `FaultConfig` axes, each on its own stream: a forward jump across a restart (downtime),
  a backward wall-clock step, and per-host skew, so a promoted follower runs on a clock offset
  from the primary's. MANIFESTO §6's "clock skew" becomes true.
- **Wire oracles** in the edge harness: real binaries over real TCP, each red before its fix.
  (1) A short-interval schedule ticks within one interval after a restart of a process that
  ran for several intervals. (2) A session past its TTL is refused after a restart. (3) An
  OIDC token whose Unix-scale `exp` is past is refused, and one whose `nbf` is past is
  accepted.
- **Sim properties** under the new axes. Cron fires at most once per catch-up and never stalls
  more than one interval past its due time. No session resolves past its `expires_at`. No job
  runs before its `due_at`. `now` never decreases across records. Each has `require` keys
  proving the axes fired, and a naive victim (an uptime clock) that fails them by name.
- **A census** lists every stored or compared `Clock` value. The sites in §1 item 1 are where
  it starts, not the whole list. Each value is covered by an oracle above, or named as not
  needing one, with the reason.

### C. Generated inputs and shrinking

- **Drawing.** A workload draws its inputs through the run, with something shaped like
  `sim.input()`: an integer in a range, a choice from a list, a shuffle, a vector of drawn
  length, a string with variation. It is plain Rust, with no DSL. Draws come from the inputs'
  own stream, and the run records the sequence of choices it consumed.
- **Shrinking.** The prior art is Hypothesis, which shrinks the sequence of choices rather
  than the values (and proptest's value trees, for contrast); both go into NEIGHBORS.md, which
  has neither today. A failing run is replayed with smaller choice sequences, and with fault
  axes turned off one at a time, and the smallest run that still fails the same check is
  kept. A smaller input can move where faults land, so a candidate counts only if it still
  fails that check. How strictly "the same failure" is matched is the builder's call; slipping
  to a different bug is the known risk. Shrinking runs by default, on the first failure of
  each check, deterministically for any `--jobs`, with a budget counted in replays.
- **The failure block** (seed, config, fired, repro: GUIDE §8's five lines) gains the shrunk
  inputs as values and the fault axes the shrunk run needs. Its repro command replays exactly
  the shrunk case. The original seed stays printed.
- **The check line counts distinct inputs**: how many distinct choice sequences the check's
  tested runs consumed. A check whose workload drew nothing says its inputs were scripted and
  every run tested the same case, and names `sim.input()` and GUIDE §8. It is a count, like
  tested and skipped, never a threshold.
- **The scaffold** (`templates/lib.rs`, `templates/sim.rs.tmpl`) posts several notes with
  drawn bodies in a drawn order. It gains a third property: an acked POST implies its
  `NoteAdded` event after recovery, so deleting `tx.emit` goes red.

### D. The output

From the 0.2.1 spec. Noah approved the shape on 2026-10-17, and the direction to lean on
comparable CLI tools: `cargo test`'s shape, with a generated case that could not test the
property reported beside passed and failed (QuickCheck's "discarded", Hypothesis's
"invalid"). The approved shape, counts illustrative:

```text
running 2 sim checks, 256 runs each, under random crashes and disk faults

check acked_note_survives_a_restart ................ ok   (88 tested, 168 skipped)
check acked_post_implies_the_echo_after_recovery ... ok   (90 tested, 166 skipped)

skipped runs hit a fault before reaching the check, so they prove nothing either way:
  acked_note_survives_a_restart
    120  the POST was never acked, so durability has nothing to prove
     31  App::open hit fault fallout
     17  the kernel loop hit fault fallout
  acked_post_implies_the_echo_after_recovery
    ...

sim result: ok. 2 passed; 0 failed. 178 of 512 runs tested a check.
rerun exactly this batch: charpente test --sim --master-seed 0x994fd0134ccf9f9e
```

Part C adds the distinct-inputs count to each check line, and the scaffold will have three
checks. The rest are the controller's calls, carried from 0.2.1's builder check; Noah has not
yet seen them in writing:

- **"Tested" means passed plus failed.** A check line with failures shows them:
  `check X ... FAILED (90 tested: 78 failed; 166 skipped)`.
- **A check that tested nothing is `untested`, never `ok`.** The result line counts it
  (`1 passed; 0 failed; 1 untested`). When every check is untested, the result line does not
  begin `sim result: ok`.
- **A check with an unmet `require` is `FAILED`**, and its line names the requirement.
- **The header goes to stderr at startup and carries the master seed**, because DESIGN §7
  promises a killed batch still shows its seed. The rerun command closes the output and
  carries `--filter` and `--runs` whenever they were given.
- **A skipped run gets a stable reason**, which the output groups and counts, plus an optional
  per-run detail that only a single-seed replay shows. `give_up` takes both, changed in place
  (§2). Reasons are capped per check, with an "and K more" line, so an app that embeds error
  text in its reason stays readable. `\n`, `\r` and `\t` print escaped.
- **A single-seed replay** speaks the same language. For a skipped run, it prints the run's
  reason and detail.
- **One vocabulary.** Now that nothing is kept for compatibility, the app-facing surface says
  run, check, tested and skipped throughout. `--universes` becomes `--runs`, and GUIDE, the
  scaffold, the coverage key `universe:gave-up` and the JSON's field names follow. Rust
  identifiers that agents copy from code (`sim_tests!`, `CHARPENTE_SEED`) keep their names.
  The platform's internal suites and internal identifiers may keep "universe".
- **`--format json` carries every fact the human output does** (reasons and their counts,
  distinct inputs, shrunk inputs), so an agent reading JSON sees what a person sees.
- **No new line for faults that fired.** The second agent eyeballed the fault counters to
  confirm that refused, throttled and slow replies actually happened. `require` keys already
  make that mechanical: an unmet one fails the check. So GUIDE §8 and the scaffold `require`
  the fault keys their properties depend on, rather than adding a line to the output.

### E. What ships

- **GUIDE.md ships inside the `charpente` crate** as its crate-level docs, so it is on docs.rs
  and in the registry copy an offline agent searches. It keeps its compile gate
  (`guide-examples`) and its pinned-text gate (`doc_truth`). Error texts that cite "GUIDE §N"
  then cite something an offline agent has. The mechanism is the builder's; cargo packages
  only files under the crate's own directory.
- **`charpente-sim` ships compiled `examples/`**: app-shaped workloads for drawn inputs, a
  modelled remote, and a restart under faults. `cargo test` compiles them, so they cannot
  drift.
- **`charpente_sim` re-exports `OutboundCall` and `OutboundReply`**, so a sim test imports
  from one crate.

### F. The small ones

- **`charpente --version` and `-V`** print `charpente <version>` and exit 0, as
  `cargo --version` does.
- **README's "Try it."** The clippy line says to run `rustup component add clippy` when the
  component is missing. The red step names `acked_post_implies_the_echo_after_recovery` and
  says what the stranger will see.
- **The scaffold declares `rust-version`**, so an older toolchain gets cargo's clear error,
  and README names the components. No `rust-toolchain.toml` (controller's call): on an
  offline box that lacks a component, a toolchain file turns "clippy is missing" into every
  cargo command failing, and the launch run's box was offline.
- **CHANGELOG.** 0.2.0's heading gets its publish date (2026-10-17) now, together with the
  0.2.0 close-out ledger line (CI run 39048921595; the first nightly edge-harness run at
  f6eb65b6, 39125650197). A 0.3.0 entry lists the breaks. No outside credits (Noah).
- **PLAN's v1.x table** gains the three rows in §3's non-goals.

## 6. How we know it worked

1. **Text pins** (hard rule 5) for every new output and refusal: green, red, unmet coverage,
   all-skipped, capped reasons, a single-seed replay of a skipped run and of a failing one, a
   shrunk failure, a check with scripted inputs, and the stale-data-directory and stale-peer
   refusals.
2. **Determinism** (§4). Every platform pinned seed and recorded batch decides identically,
   except at the named steps, and each step's before and after are recorded. Two runs of one
   batch, and runs at `--jobs 1` and `--jobs N`, print byte-identical output.
3. **The clock oracles** (B), each red before its fix and green after, plus fresh-seed sim
   evidence for the new properties at the repo's bar (CLAUDE.md: green over N fresh seeds,
   with N stated).
4. **The inputs oracle.** A fixture app with the second agent's bug class: a merge that must
   keep the largest amount. Its "latest wins" mutant survives a scripted workload, which is
   the control that shows the oracle is needed, and dies under the generated one. The shrunk
   failure is pinned: two arrivals, the later one smaller.
5. **Mutation.** `charpente test --mutants` over the new code in charpente, charpente-sim and
   charpente-cli: every viable mutant is caught, or argued equivalent by name.
6. **The gate.** fmt, clippy with the deny-list, and `cargo test --workspace --no-fail-fast`
   counted by `test result: ok`; then CI green and the next nightly edge-harness run green.
7. **A stranger reads it.** Re-run the launch run's rehearsal: the tools in
   `docs/experiments/2026-10-launch-run/tools/`, the packaged 0.3.0 crates, a fresh box,
   `BRIEF.md` byte-identical, and a headless Opus agent with only the README. After its report,
   one neutral follow-up, recorded verbatim: "In two or three sentences, what did the last sim
   run you did tell you?" It passes when, across the report and that answer:
   - (a) for each check, it says correctly whether the check held and how many runs tested it;
   - (b) it gives at least the most common skip reason, correctly;
   - (c) it describes the red run's shrunk input correctly;
   - (d) nothing it says calls the output overstated, misleading or unclear;
   - (e) every claim it makes about charpente is right, censused the way the launch run's
     were.

   This bar is written before the run. A miss is a finding about the output: fix it and run a
   new attempt, recording both. It is never argued away.
8. **A docs-only build** (M3 sub-project 3's bar; Noah, 2026-10-22). A fresh agent, offline,
   given only what ships in the 0.3.0 crates, builds an app in a new domain whose correctness
   rests on an order-sensitive merge. The brief is written and committed before the run. It
   passes with zero framework patches, zero Criticals in review that a platform oracle should
   have caught, and `charpente test --mutants` clean over its sim properties with no hand
   mutation pass. Findings are ledgered as testimony, and any platform defect it finds is
   fixed before the publish.
9. **After the publish** (Noah's hand), the registry smoke, as for 0.2.0: install,
   `--version`, `new`, clippy, sim.

**Order:** A, B, C, D, E, F, then 7 and 8, then the publish. Behaviour comes before rendering,
so D's determinism check runs against the baseline recorded after B and C.
